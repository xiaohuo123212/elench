# 成本记账单位：解释器把什么算作「一个操作」

> 本文回答一个问题：**κ 里的"1"到底指什么？**
> 如果这一条不清楚，读 `κ = 4 + n(xs)×12` 时就没法判断它是不是上界。

## 0. 一句话

> **1 个操作 = 执行一条语句，或者求值一个表达式节点，或者走一轮循环。**

κ 和实测（`ops`）用的是**同一个单位**——这是"成本可对账"的前提。
实测由解释器自己数（`ELENCH_COUNT_OPS=1`），静态侧由 `CostInterp` 算，
两边都按下面这张表。

## 1. 表达式：每个节点 1 步

| 构造 | κ 怎么记 | 例子 |
|---|---|---|
| 整数字面量 | **1** | `0`、`42` |
| 路径（变量名） | **1** | `i`、`xs` |
| 二元运算 | **1 + 左右子树** | `i + 1` → 1+1+1 = **3** |
| 比较 | 同上（比较也是二元） | `i < n` → **3** |
| 括号 | **0**（只算里面的） | `(i)` → 与 `i` 同价 |
| 方法调用 | **max(3, 2 + 实参合计) + 接收者** | `xs.at(i)` → max(3,2+1)+1 = **4** |
| 零实参方法 | 同上，`length()` 固定记 **3** | `xs.length()` → 3 + 1 = **4** |
| 下标 `a[...]` | **1 + 全部子节点** | |
| 元组 `(a, b)` | **1 + 各元素** | |
| 结构体字面量 | **1 + 各字段表达式** | |
| 类型名（如 `Vec`） | **1** | |
| `(...)?`（try） | **1 + 子表达式** | |

**为什么方法调用是 `max(3, 2+实参)` 而不是简单的"1"**：
解释器对一次方法调用要走 **节点 → 接收者 → 每个实参 → 派发** 这几步。
`xs.length()` 没有实参，但派发本身要 1 步，所以记 3（再 + 接收者 1 = 4）。
`a.at(i*dim + k)` 的实参是 3 个节点（2 叶子 + 1 加法 + 1 乘法 = 5 步），
记 2+5 = 7（+ 接收者 = 8）——**LE36 就是这里漏了实参子树，导致 `matmul` 的 κ 少算**。

## 2. 语句：每条 1 步，加上它包含的表达式

| 构造 | κ |
|---|---|
| `return e;` | 1 + κ(e) |
| `x = e;` | 1 + κ(e) |
| `x += e;`（复合赋值） | 1 + κ(e) |
| `u64 x = e;`（声明） | 1 + κ(e) |
| `const T x = e;` | 1 + κ(e) |
| 表达式语句 `f(x);` | 1 + κ(e) |
| 空语句块 `{ }` | 0 |

## 3. 控制流

| 构造 | 每轮 / 整体 |
|---|---|
| 条件分支 if / else | 1 + κ(条件) + **max**(κ(真臂), κ(假臂)) —— 只走一条路 |
| while 循环 | 轮数 ×（**1**（记账）+ κ(条件) + κ(体)） |
| 区间遍历 for-in | n(xs) ×（同上） |
| 数值区间遍历 `a..b` | (b−a) ×（同上） |
| `match` | 1 + κ(被匹配) + **max**(各臂) |
| `?!label(...)` | 有分档表 → **分段**（该段候选的 κ）；无表 → **max**(所有候选) |
| `parallel { … }` | 各任务成本之和；**v0 按单线程语义**（并发耗时不在承诺内） |

**"只走一条路所以取 max"** 是这套记账里最容易被误读的一条：
`if` 两臂不是相加，是取较贵的那条。同理 `?!` 的候选也不是相加。

## 4. 函数：序言与结尾

一次调用 = **2 步固定开销**（进入 + 返回），加上函数体的 κ。
这就是为什么最小程序 `return 0;` 的 κ 是 **2** 而不是 1。

## 5. 实测核对（2026-11-02，n=4）

同一段代码，左边 κ、右边解释器实测：

| 构造 | κ | 实测 |
|---|---|---|
| `return 0;` | 2 | 2 |
| `i` | 4 | 4 |
| `i + 1` | 6 | 6 |
| `xs.length()` | 5 | 4 |
| `xs.at(i)` | 7 | 7 |
| `xs.at(i) >= 3` | 9 | 9 |

（含函数固定 2 步 + `return` 1 步，所以 `return 0;` 是 2：**2 是"进入+返回"，
`return` 语句本身不额外计**；`i` 那条 4 = 进入 + 声明 `u64 i = 0;`（1+1）+ 返回。）

## 6. 两处已知的 ±1 不对齐（诚实列出）

| 构造 | 现象 | 影响 |
|---|---|---|
| `(expr)` 括号 | κ 记 **0**，实测每层 **+1** | 单看会显得 κ 偏低；整程序里被别处的余量吸收 |
| `expr;` 表达式语句 | 实测比 κ **多 1** | 同上，方向是"实测更贵" |

这两条都**不会**让 κ 变成非上界（它们让 κ 偏小，但代价是余量变小）。
`tools/kappa_vs_ops.py --strict` 会在整程序上检查"是否真的破界"。

## 7. 自己验证

```bash
# 看某个函数跑一次的真实操作数（与 κ 同单位）
elench stats 文档/入门/例子/hello hello --ops

# 看 κ
elench cost 文档/入门/例子/hello

# 全量对账：κ 是否压得住最坏实测
python tools/kappa_vs_ops.py --strict
```

> 记住：**`ops` 是"操作数"，不是纳秒**。它不受 CPU、缓存、编译器优化影响，
> 所以同一个程序在同一份输入上，今天和明天的 `ops` 必须一模一样。
