# 示例：`spec` / `choose` / `?!` 一起看

**这例子要说明什么**：

> **一个函数里有一步，走哪条路都能算对，但快慢取决于输入规模与机器——这一步交给测量；其余逻辑仍然由写代码的人负责。**

**难度**：入门。会写循环就够。

---

## 0. 三个角色，三种写法

| 角色 | `.tu` 里长什么样 | 有 `spec` 吗 | 有 `benchmodel` / `target` 吗 |
|---|---|---|---|
| **主函数**（对外入口） | `spec binary_search(...) { … }` | ✅ 有 | ✅ 有 |
| **算法内核**（被测量挑选） | `over {search_linear, search_binary, search_interp pending};` | ❌ **没有** | ❌ **没有** |
| 普通私有函数 | `spec helper(...) { … }` | ✅ 有 | 可省 `target` |

> **一眼就能看出谁是主函数**：`spec` 开头的是契约；算法内核没有自己的声明，只在宿主 `spec` 的 `choose` 里由 `over` 名单点出。
> **认主函数不需要去查 `choose`。**

**为什么内核不写 spec**：它的效果和成本约束**已经从宿主那边给了**（F-9-c / F-9-d）。
再写一份，等于同一件事写两遍——**两处一旦不一致，读者无从判断哪个算数**。

---
## 1. 先划清一条线：`?!` 标的是"一步"，不是"整个函数"

| 用法 | 判定 |
|---|---|
| 函数有自己的逻辑，**中间某一处**用 `?!` | ✅ **正确** |
| 函数体只有 `return ?!L(xs);` | ❌ **`E-Choose-WholeBody`** |

**为什么禁止整函数转发**：

> 那就不是"选算法"，是**用测量代替设计**——它没有说"这一步要做什么"，只说了"挑一个能跑的"。
> 若不禁止，每个函数都可以被复制成两份让测量去挑，**生成者就再也不用想清楚任何一个算法的结构**。

---

## 2. 任务

判断一个有序数组里有没有 `key`，有就给出它的下标。

**函数要做的四件事**：

1. 取长度 `n`
2. `n == 0` 直接返回 `NotFound`
3. **定位 `key` 的下标** ← **这一步有三种候选算法，交给测量**
4. 返回下标

---

## 3. `search.tu` —— 声明全在这里

`样例/search.tu` 全文（**这里没有 `cost`**：cost 由编译器算，写到编译器生成的 `search.cost.yaml`）：

<!-- @include search.tu#spec -->
```
error SearchError;

// 二分查找的循环条件。
// 循环体里区间每次至少减半，所以圈数上界是 log2(区间长度)——这是算法性质，
// 无法由条件形态推出（规格 T13 来源①），只能由谓词的 repeats 声明（来源②）。
spec in_range(u64 lo, u64 hi) -> bool {
    effects { };
    repeats log(hi - lo);
}

spec binary_search(
    const Vec<u64>& xs, u64 key) -> u64! {
    effects { alloc };
    requires is_sorted(xs);

    benchmodel {
        data {
            xs = sorted_u64s();
            key = any_of(xs);
        }
        scale {
            xs in range(1, 1048576, *2);
        }
        seed = 1;
    };

    target {
        time: { max: O(log(xs.length())) },
        allocation: { max: 0 },
    }
    ;

    choose search_impl(const Vec<u64>& xs, u64 key) -> u64! {
        over {
            search_linear,
            search_binary,
            search_interp pending
        }
        ;
        objective time;
    };
}
```
<!-- @end -->

三个候选只在这份 `over` 名单上出现，没有自己的声明，也没有 `spec` / `benchmodel` / `target`——它们的契约由宿主 `binary_search` 给出（F-9）。

## 4. `search.eln` —— 实现全在这里

`样例/search.eln` 全文（签名 + 函数体，零声明；候选写在宿主 `func` 之后的 `kernels` 块里）：

<!-- @include search.eln#fn -->
```
// `in_range` 是普通函数：spec 在 .tu 里（含 repeats），实现就在这里。
// 它只被用作 while 条件——区间未空就继续。
func in_range(u64 lo, u64 hi) -> bool {
    return lo < hi;
}

pub func binary_search(
    const Vec<u64>& xs, u64 key) -> u64! {
    const u64 n = xs.length();
    if (n == 0) {
        return Err(SearchError::NotFound);
    }
    const u64 idx = (?!search_impl(xs, key))?;
    return idx;
} kernels search_impl(
    const Vec<u64>& xs, u64 key) -> u64! {
    search_linear {
        u64 i = 0;
        while (i < n) {
            if (xs.at(i) == key) {
                return i;
            }
            i = i + 1;
        }
        return Err(SearchError::NotFound);
    }
    search_binary {
        u64 lo = 0;
        u64 hi = n;
        while (in_range(lo, hi)) {
            const u64 mid = lo + ((hi - lo) / 2)?;
            const u64 v = xs.at(mid);
            if (v == key) {
                return mid;
            }
            if (v < key) {
                lo = mid + 1;
            } else {
                hi = mid;
            }
        }
        return Err(SearchError::NotFound);
    }
}
```
<!-- @end -->

**`binary_search` 的四步里有三步是它自己的**，只有"定位 `key`"这一步换成了 `?!`。

## 5. 逐块讲解

下面几个片段摘自 §3 / §4 引入的那两份样例（全量在那里，这里只留要点）。

### ① `spec` —— 写**意图**，不写**实际**

```
    target {
        time      : { max: O(log(xs.length())) },
        allocation: { max: 0 },
    };
```

| 部分 | 含义 | C++ 对照 |
|---|---|---|
| `spec` | 对外承诺什么 | 一个**有强制力**的注释块 |
| `target` | 希望的成本上限 | 你想写在注释里的话，现在必须写对 |
| `allocation: { max: 0 }` | 一次内存都不许要 | 不许 `new` / `malloc` |

**这里没有 `cost`**：

> **`cost` 是"实际花了多少"，编译器算；`target` 是"希望花多少"，人写。**

### ② `benchmodel` —— 说清"在什么输入下量"

```
benchmodel { xs: sorted_u64s(max_len = 16), key: any_u64(), };
benchmodel { xs: sorted_u64s(min_len = 1000000), key: any_u64(), };
```

一个算法在 16 个元素上快，在 100 万个元素上可能慢。**不给模型，测量就是假的。**

### ③ `choose` —— 只说三件事

（宿主 `spec` 的其余子句见 §3，这里只留 `choose`。）

<!-- @include search.tu#choose -->
```
    choose search_impl(const Vec<u64>& xs, u64 key) -> u64! {
        over {
            search_linear,
            search_binary,
            search_interp pending
        }
        ;
        objective time;
    };
```
<!-- @end -->

| 子句 | 说什么 |
|---|---|
| `over` | **候选是谁**——同模块、同签名的候选 |
| `benchmodel` | **在哪些场景下量**——引用 spec 已声明的场景名 |
| `objective` | **按什么目标选**——四选一，不能自由文本 |

**它不说"选哪个"**——那是测量的输出。

### ④ `?!search_impl(xs, key)` —— 表达式里的一处"未定"

- **类型**：由 `kernels` 头的签名决定（`fn(Vec<u64>, u64) -> u64!`）
- **成本**：取**所有候选的上界**
- **谁填**：`dsh refresh-dispatch` 生成的表

## 6. 编译器产出：`search.cost.yaml`

```yaml
# search.cost.yaml —— 由 dsh 生成，请勿手工修改
# 重新生成：elench cost search
# 排序：本次有变化的条目在前（标 ▲），其余保持上次顺序

functions:
  binary_search:                 # ▲ new
    uses_choice: [search_impl]   # 它的成本里有"一步"来自测量上界
    time:        {min: "n",   max: "n"}      # 取候选上界：search_linear 是 n
    allocation:  {min: "0",   max: "0"}
    debt:        {time: n vs log(n), allocation: none}

  search_linear:                 # ▲ new
    time:        {min: "n",   max: "n"}
    allocation:  {min: "0",   max: "0"}
    debt:        {time: none, allocation: none}

  search_binary:                 # ▲ new
    time:        {min: "log(n)", max: "log(n)"}
    allocation:  {min: "0",   max: "0"}
    debt:        {time: none, allocation: none}
```

**`uses_choice: [search_impl]` 这一行是给信任区看的**：

> 它说：「这个函数的时间上界里，有一段不是我静态推出来的，而是**取候选里最慢的那个**。」
> 报告读到这里，就知道这个数字依赖哪个 `choose` 块。

**`binary_search` 的 `time` 是 n，比 `target` 的 `log(n)` 宽**——差额记成债务（`debt: time`），不阻断构建（C-COST-2），但 MUST 可见：
慢的那个候选（`search_linear`）在哪，债就在哪。

**阶不同，分界点仍然只能测**——`search_linear` 是 n、`search_binary` 是 log(n)；
"多大的数组该换成二分"是测出来的（见 §7 的分档表），不是读代码读出来的。

## 7. 测量的产出：`search.dispatch.yaml`

```yaml
# search.dispatch.yaml —— 由 dsh refresh-dispatch 生成，可提交、可审查
search_impl:
  axis: n
  buckets:
    - { up_to: 4096, use: search_linear }
    - { up_to: null, use: search_binary }
```

**意思**：小数组用线性扫描（示例值），大数组用二分。

**这张表必须存在才能构建**——源码有 `?!search_impl(...)` 而表缺失，构建直接失败并提示 `refresh-dispatch`。

## 8. 这个设计挡住了什么

### 挡住「混一个慢的内核进来」

假设 AI 想再加一个候选 `search_nested`（套两层循环，O(n²)），指望"测出来差不多"：

| 关卡 | 结果 |
|---|---|
| 候选自己没有 `target`（F-9）；它的成本只经由宿主的 `?!` 上界体现 | **`search_nested` 的成本是 n²，把宿主 `binary_search` 的上界抬到 n²** |
| 就算把宿主的 target 改宽，`?!` 仍取**所有候选上界** | `binary_search` 的 `time` 变成 **n²**，再次违反（改宽也要改到 n² 才成立） |

> **上界规则让"混进来"在数学上不可能成功**——只要候选里有一个慢的，整个函数就慢。

### 挡住「整函数转发」

```
pub func binary_search(xs: Vec<u64>, key: u64) -> u64! {
    return ?!search_impl(xs, key);   // ❌ E-Choose-WholeBody
}
```

**报错理由**：这里没有"做什么"，只有"挑一个"。

### 挡住「不测就上」

| 情况 | 行为 |
|---|---|
| 有 `?!` 但无 dispatch 表 | **构建失败** |
| 表存在但源码改过 | 提示表过期，重新生成 |
| 想手写切换点 | **语法里没有位置** |

---

## 9. 四个概念的分工

| 概念 | 回答什么问题 | 谁回答 |
|---|---|---|
| **`spec`** | 这个函数承诺什么？ | **人**（`target` 批准后冻结） |
| **`choose`** | 有哪些算法可选、在什么输入上比什么？ | **AI** |
| **`?!`** | 这一处具体用哪个？ | **测量** |
| **`cost` 表** | 实际花了多少？ | **编译器** |

> **一句话**：**人管"要什么"，AI 管"有哪些选项"，机器管"选哪个"和"实际多快"。**
