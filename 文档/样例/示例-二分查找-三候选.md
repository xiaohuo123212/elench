# 示例：二分查找 · 三个候选

**用途**：演示 `target` / `?!` / `pending` 三者如何在**一个函数**上协同。
**重要**：本文的判定表是**按规则手工推演**，**不是编译器输出**（编译器尚未实现）。
**标注**：凡 `← 推演` 的结论，都是人按 B-6 / B-9-a / B-16 逐条算出来的。

---

## 1. 人写：契约（`.tu`）

```
// search.tu —— 人读这一份，签字
spec binary_search(xs: []u64, key: u64) -> Result[u64, SearchError] {
    effects    {alloc};
    requires   is_sorted(xs);

    model small  { xs: sorted_u64s(max_len = 16), };
    model medium { xs: sorted_u64s(min_len = 1_000, max_len = 10_000), };
    model large  { xs: sorted_u64s(min_len = 1_000_000), };

    target {
        time      : { max: O(log(xs.length())) },
        allocation: { max: 0 },
    };

    choose search_impl(xs: []u64, key: u64) -> Result[u64, SearchError] {
        over      {search_linear, search_binary, search_interp pending};
        usemodel  {small, medium, large};
        objective time;
    } end choose
} end spec
```

**人只写了这一段。** 没有算法、没有循环、没有边界条件。

**三个关键点**：

| 元素 | 作用 |
|---|---|
| `target: time max O(log n)` | **意图**：我要对数级 |
| `over {三个}` | 候选名单：`over` 本身就是声明，不再有独立的 `kernel` 声明 |
| `search_interp pending` | **声明**：这个候选我还没写（`pending` 是裸词标记） |

---

## 2. AI 写：实现（`.eln`）

```
// search.eln
pub fn binary_search(xs: []u64, key: u64) -> Result[u64, SearchError] {
    val n = xs.length();
    if n == 0 { return Err(SearchError::NotFound); } end if
    val idx = ?!search_impl(xs, key);          // ← 只有这一步交给测量
    return idx;
}
```

> **注意 B-15**：这条路已经接近"整个函数体"，但仍有 `if n == 0` 的边界处理。
> **如果 AI 写成 `return ?!search_impl(xs, key);` 一行，会报 `E-Choose-WholeBody`。**

### 候选一：线性扫描（**故意写一个不合格的**）

```
// 紧接在上面那个 fn 后面：`} kernels search_impl(...) -> ... {`
kernels search_impl(xs: []u64, key: u64) -> Result[u64, SearchError] {
    search_linear {
        var i = 0;
        while i < xs.length() {
            if *xs.at(i) == key { return Ok(i); } end if
            i = i + 1;
        } end while
        return Err(SearchError::NotFound);
    }
```

**成本：`O(n)`。** ← 推演（T11：`n` 次迭代）

### 候选二：二分查找

```
    search_binary {
        var lo = 0;
        var hi = xs.length();
        while lo < hi {
            val mid = lo + (hi - lo) / 2;
            val v = *xs.at(mid);
            if v == key { return Ok(mid); } end if
            if v < key { lo = mid + 1; } else { hi = mid; } end if
        } end while
        return Err(SearchError::NotFound);
    }
} end fn          // ← 整块只有一个 `end fn`
```

**成本：`O(log n)`。** ← 推演（区间每次减半）

### 候选三：插值查找（**还没写**）

```
// search.eln 的 kernels 块里没有 search_interp —— 与 over 里的 `search_interp pending` 一致
```

## 3. 手工推演：编译器会说什么

### ① 含线性扫描时

| 步骤 | 结论 |
|---|---|
| 各候选成本 | `search_linear = O(n)`、`search_binary = O(log n)` |
| `?!` 的成本（**B-6 取 ⊔**） | **`O(n)`** |
| 与 `target` 比 | `O(n) > O(log n)` |
| 结果 | **债务 `time`**（C-COST-2），不阻断构建 |

```
$ dsh check       ← 推演

binary_search                        debt
├─ target   time O(log n)
├─ cost     time O(n)             ← 被 search_linear 抬高
└─ 债务     time: O(n) vs O(log n)

choose search_impl                   incomplete
├─ over     search_linear, search_binary, search_interp
├─ pending  search_interp
└─ 成本上界  O(n)                 ← 由最慢候选决定
```

**这就是"倒逼"**：**只要候选池里有一个 O(n) 的实现，整个 `?!` 就是 O(n)**，债务立刻显形。

**B-6 已经删掉了"每个候选必须满足 target"那条硬错误**——不需要它，债务机制已经把问题暴露了。

### ② 删掉线性扫描后

| 步骤 | 结论 |
|---|---|
| 剩余候选 | `search_binary = O(log n)`（`search_interp` 在 pending） |
| `?!` 成本 | `O(log n)` |
| 与 `target` 比 | **相等 → 无债务** |
| `dsh check` | **通过** |
| `dsh build` | **失败**（`pending` 未清，B-17） |

```
$ dsh check       ← 推演
binary_search                        incomplete       ✓ 契约层通过
choose search_impl                   incomplete       ✓ 无债务
  pending: search_interp                              ← 未实现

$ dsh build       ← 推演
✗ E-Choose-Incomplete
  search_impl 仍有 pending 候选：search_interp
```

**这正是"两条尺子"**：**能查、不能建。**

### ③ 插值查找写完之后

```
    // 写完后：把 over 里的 `search_interp pending` 改成 `search_interp`
    search_interp {
        …
    }
```

| 步骤 | 结论 |
|---|---|
| 删掉 `pending` 标记 | 声明与实际一致（B-16 双向校验） |
| `?!` 成本 | `O(log log n) ⊔ O(log n)` = **`O(log n)`** |
| 与 `target` 比 | `O(log n) ≤ O(log n)` ✓ |
| `dsh build` | **通过** |
| `dsh bench` | 测三个模型点，生成分档表 |

```
$ dsh dispatch       ← 推演
search_impl:
  { up_to: 1000,      use: search_binary }
  { up_to: 1000000,   use: search_interp }
  { up_to: null,      use: search_binary }     ← 大数组回退（插值在非均匀分布上退化）
```

**注意最后一行**：`search_interp` 在**非均匀分布**上会退化成 O(n)。
**而 `target` 要求 O(log n)**——**所以它只能被放在测过的区间里**，超出区间必须回退。

> **这不是我们额外加的规则，是 `⊔` 规则的直接后果**：
> 因为 `?!` 的成本按**最坏候选**算，所以任何一个候选退化都会立刻抬高标准。

---

## 4. 这个例子演示了四件事

| # | 机制 | 在例子里怎么体现 |
|---|---|---|
| 1 | **`target` 是人写的意图** | `O(log n)`，AI 不改它（D7 冻结） |
| 2 | **`?!` 取所有候选上界** | 混入 `O(n)` 的线性扫描 → 整个 `?!` 变 `O(n)` → 债务 |
| 3 | **`pending` 是声明** | 插值查找没写 → 必须标 `pending` → `check` 过、`build` 不过 |
| 4 | **分档表可审** | 生成的表里"大数组回退"这个决定写在文件里，可 diff |

## 附：与另一份候选写法（不是本语言）的对照

常见描述会用属性写法，**那不是本语言的语法**：

| 常见误写 | 本语言 |
|---|---|
| `#[cost(target="O(log n)")]` | `target { time: { max: O(log(xs.length())) } }` |
| `#[variant]` | `choose` + `kernels` 块 + `?!` |
| `planned` 状态 | `over` 里的 `pending` 标记（状态由 `.eln` 里有没有这个候选体决定） |

**记这一条的理由**：本项目已多次收到用上述错误语法描述本语言的分析文本。
**若照抄，会写出我们语言里不存在的东西。**
