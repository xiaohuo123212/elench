# 对抗语料（T-02）

> 2026-11-06。**为什么有这份**：试点里 `unknown` 的 11 个**全部**是 N1（压根没写 target），
> N2 = 0。读者第一反应必然是"你挑的语料"。
> 这里放**都写了 target、但当前判不了或判不准**的函数——**不美化，判不了就写判不了**。

## 归因分级（本文件定义）

| 类 | 含义 |
|---|---|
| **N1** | 没写 target（不适用契约） |
| **N2** | 写了 target，但**判不了**（κ 是 ⊤，或尺寸量与 target 对不上） |
| **N3** | 判了，但**上界过松**（比真值差一个量级） |
| **N4** | 判了且对，但**代价口径**与使用者的直觉不同（需要解释） |

## 语料与实测结果（`corpus/adversarial/adv.{tu,eln}`）

| # | 函数 | target | 实测 κ | 判定 | 归因 |
|---|---|---|---|---|---|
| 1 | `partition` | `O(n)` | `8 + n(hi)×36 + …` | 无法判定 | **N2**：κ 用 `hi`，target 用 `n`（E23） |
| 2 | `two_pointer_dedup` | `O(n)` | `15 + n(xs)×31 + …` | 无法判定 | **N2**：κ 用 `xs`，target 用 `n` |
| 3 | `linear_probe` | `O(1)` | `⊤` | 无法判定 | **N2**：循环守卫 `table[i] != 0` 推不出圈数 |
| 4 | `sliding_sum_max` | `O(n)` | `n(k)×16 + n(xs)×29 + …` | 无法判定 | **N2**：两个尺寸量都对不上 `n` |
| 5 | `heapify_up` | `O(log(n))` | `n(i)×39 + …` | 无法判定 | **N2**：κ 用 `i`；**且**这段其实是 log 循环，但更新写成 `i = p`（`p = (i-1)/2`），**不是** `i = i / 2` 的字面形状 |
| 6 | `gcd_loop` | `O(log(n))` | `⊤` | 无法判定 | **N2**：`b = a % b` 的推进推不出圈数 |

**6/6 全部 N2**——**N2 > 0，且每条都有归因**。

## 这份语料说明了什么

1. **主流失效不是"不支持某个语法"，是"尺寸量命名对不上"**：6 条里 4 条（#1 #2 #4 #5）的
   κ 本身算出来了，只因变量名与 target 里的 `n` 不是同一个符号而**判不了**。
   **这是一个能改进的具体点，不是"语言能力不够"**。
2. **工具没有撒谎**：判不了就说"无法判定"，没有拿一个偏小的界冒充通过。
3. **#5 暴露 `_log_loop` 的边界**：它只认 `i = i / 常量` 的字面形状；
   `i = p`（而 `p = (i-1)/2`）这种**中转变量**认不出，于是退化成线性。

## 怎么复现

```bash
python src/dsh.py cost corpus/adversarial/adv
```

## 怎么用这份语料

- 改进后重跑，**看哪几条从 N2 掉出去**——这是"真的变强了"的证据；
- **不要**为了让它变绿而改 target 的写法来迁就工具（那是自己骗自己）。

## 改进记录

### 2026-11-06：长度别名统一（`const n = xs.length()` → `n(xs)`）

**改了什么**：`target_cost` 现在会把 target 里的名字按函数体内的
`<局部名> = <容器>.length()` 映射回容器，于是 `O(n)` 与 κ 侧的 `n(xs)` 是同符号。

**跑出来**：

| 函数 | 改前 | 改后 |
|---|---|---|
| `two_pointer_dedup` | 无法判定（`n(xs)` vs `n(n)`） | **✓ 达标** |
| 其余 5 条 | 无法判定 | 仍无法判定（原因见下） |

**只掉出去 1 条，不是预期的 2 条**——剩下几条的障碍不在别名：

| 函数 | 为什么仍判不了 |
|---|---|
| `partition` | κ 用 `hi`（**下标**，不是尺寸）。要把它映射成 `n(xs)` 需要前提 `hi <= xs.length()`，**这个前提写在 `requires` 里，而当前 target 解析不看 requires** |
| `heapify_up` | 同上，`i` 是下标 |
| `sliding_sum_max` | 别名已生效，但 κ 里还有 `n(k)`——`k` 是窗口大小，**除非有 `requires k <= n`，否则 `O(k+n)` ⊆ `O(n)` 不成立**，判不了是对的 |
| `linear_probe` / `gcd_loop` | 圈数推不出（`⊤`），与尺寸命名无关 |

**结论：剩下的瓶颈是 `requires` 没参与尺寸推导**，不是符号命名。这是下一个可做的具体点。

### 下一个具体点：让 `requires` 参与尺寸推导

上一步只让 1 条掉出 N2。剩下两条（`partition` / `heapify_up`）卡在同一个前提上：

    要证明 `O(hi) ⊆ O(n)`，需要 `requires hi <= xs.length()`

**这个前提本来就该写在 `requires` 里**，而当前 target 解析**不看 requires**。
`sliding_sum_max` 同理（需要 `requires k <= n` 才能把 `O(k+n)` 收成 `O(n)`）。

**所以下一个可做项不是继续改命名，是"让 requires 参与尺寸推导"。**
没做是因为它需要先定义 `requires` 的语义（它现在是给运行期/生成器看的，不是给成本推导看的）。

### 2026-11-06（二）：环形计数器 → `probe_len` 达标

**前提约定（确立）**：`κ` 是**对终止执行的**上界（部分正确性口径）——不终止的执行没有成本。
所以 `i = (i + 1) % len` 这类环形计数器，圈数 ≤ len **不需要终止性前提**。

**改了什么**：认 `i = (i + 1) % E` 形状（`E` 能翻成尺寸量），给出 `Bound(size(E))`。
（踩到的坑：`(i + 1)` 是 **paren 节点**，不剥括号形状永远匹配不上。）

**跑出来**：

| 函数 | 改前 | 改后 |
|---|---|---|
| `probe_len`（新加了用 `table.length()` 当模数的版本） | — | **✓ 达标**（κ ≤ `7 + n(table)×16 + 16 + 2`） |
| `linear_probe`（老的 `% cap` 版本） | `⊤`（无法判定） | **▲ 债务**（κ ≤ `4 + n(cap)×13 + 13 + 2` vs target `O(1)`） |

**`linear_probe` 从"判不了"变成"判为超支"——这是变强了，不是变坏**：
它的 `O(1)` 是最坏情况下的假话，工具现在能把它**证伪**，而不是只能说"不知道"。
要让它通过，要么改成 `O(table.length())`（用 `probe_len` 那种写法），要么显式声明建模假设。

### 2026-11-06（三）：欧几里得成语 → `gcd_loop` 从 ⊤ 变成 log2

**为什么这条只能"认形状"**：圈数来自**数论**（Lamé 定理，1844）——
每两步规模至少减半（`b ≤ a/2` 时一步减半；`b > a/2` 时 `q=1, r=a−b<a/2`，两步减半）。
**这不是程序形状能推出来的**，所以规则写成"认出这一个成语"，认不出就不给界。

**判据写死**：守卫 `b != 0` / `b > 0`，循环体**恰好三条**直接语句 `t = b; b = a % b; a = t;`。
多一条就不认（语料测试里有这条反例）。

**跑出来**：

    gcd_loop   κ ≤ log2(n(a))×14 + 14 + 2    target O(log(a))    ✓ 达标

**顺带修了一处 spec 错误**：原来 target 写 `O(log(n))`，但这个函数的参数是 `a, b`——
**根本没有 `n` 这个量**。改成 `O(log(a))` 之后符号才对得上。

## 语料现状（8 条）

| 判定 | 条数 | 都是谁 |
|---|---|---|
| ✓ 达标 | **3** | `two_pointer_dedup`、`probe_len`、`gcd_loop` |
| ▲ 超支（**证伪**，不是未知） | 1 | `linear_probe`（`O(1)` 是最坏情况下的假话） |
| ? 无法判定 | 3 | `partition`、`sliding_sum_max`、`heapify_up`（都要 `requires` 那条线） |

**N2 从 6 降到 3。**

### 2026-11-06（四）：requires 进成本域 → 未知归零

**实现**（三处）：`facts_of_spec()` 从 requires 提 `A ≤ B`；`compare(impl, target, facts)`
在符号不一致时按事实**弱化**并重比；`dsh.py` 两个输出路径传 facts。

**三条硬约束**：只认 requires（不从 `xs[hi]` 推断）、无 requires 时行为不变、note 标出假设。

**语料最终状态（7 条）**：

| 判定 | 条数 | 谁 |
|---|---|---|
| ✓ 达标 | **6** | partition / sliding_sum_max / heapify_up / two_pointer_dedup / gcd_loop / probe_len |
| ▲ 超支（**证伪**） | 1 | linear_probe —— `O(1)` 在 worst case 下是假话 |
| ? 未知 | **0** | — |

**同时修了三处我自己的 spec 错误**：`partition` / `heapify_up` / `gcd_loop` 的 target
里写了不存在的符号 `n`（它们的参数分别是 `xs,lo,hi` / `h,i` / `a,b`）。
**那不是工具的问题，是我写 target 时想当然。**

**要注意**：partition 等三条现在"达标"的前提是**作者写了 requires**。
没有那条前提，它们仍然判不了——工具变的是**会读人写的前提**，不是"自己变聪明"。
