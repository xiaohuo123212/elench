# 为什么界会松：`κ` 推导的两个边界

> **本文回答**：为什么"实现明显更好"的代码，`target` 也只能写得松？松了多少？能不能修？
>
> 结论先给：**有两类不同的原因，一类可修（内层循环的总次数），一类很难修（数据结构不变式）**。前者影响面大得多，而且**它和摊还无关**。

---

## 0 先把摊还排除掉

这门语言只承诺「**每一次调用的最坏上界**」——不承诺期望，不承诺跨调用的摊还（见 [能力边界](能力边界.md) §2.3）。所以：

- **随机化结构**（跳表、哈希表）：没有最坏 `log n`，诚实契约就是 `O(n)`。**不是松，是真相**。
- **跨调用摊还**（`α(n)`）：契约形状是"单次调用"，**模型之外**。

**但下面两类不是摊还，它们都发生在一次调用之内。**

---

## 1 第一类：内层循环的「总次数有界」（**可修，影响大**）

### 现象

`κ` 对循环的口径是「**每圈取最坏那圈 × 圈数上界**」。于是嵌套循环天然被算成乘积：

```text
while (i < n) {          // 外圈 n
    while (j < n && …)   // 内圈最坏 n
        j = j + 1;
    i = i + 1;
}
→ κ = n × n
```

**但真实世界里，内层循环的总次数经常只有 `O(n)`**——因为内层计数器**只增不减**，而它上界是 `n`。

### 三个真实例子

| 算法 | 内层循环 | 真实总次数 | 现在算成 |
|---|---|---|---|
**KMP 的 `build_lps`** | `while (k > 0 && p[i] != p[k]) k = lps[k-1]` | `k` 只减，总共 ≤ `m` 次 | `m × m` |
**单调栈** | `while (stack 非空 && top < a[i]) pop()` | 每个元素**最多入栈出栈一次** → ≤ `n` | `n × n` |
**双指针 / 滑动窗口** | `while (j < n && 条件) j++` | `j` 只增 → ≤ `n` | `n × n` |

### 实测代价

移植 KMP 时（`_tier_a/string_match`）：

```text
build_lps 单独写 O(pattern.size())  →  ▲ 超标
只有写成 O(m²) 才通过
```

**结果**：`kmp_search` 承诺 `O(m²)`，对整个 KMP 只能写 `O(n·m²)`；而真值（含 lps 的摊还）是 `O(n + m)`。**写真实值会被判债务。**

（对比：正则回溯那个是**真指数**，退 `⊤` 是对的；这里不是。）

### 能不能修

**能，而且规则很窄。**

**判据**：内层循环的计数器满足三条：

1. **单调**：只增（或只减），且赋值都是 `j = j + c` / `j += c` / `j++`；
2. **只在下界/上界被推进**：`j` 不在循环内被重置（`j = 0`）；
3. **有界**：`j ≤ n`（由守卫给出）。

那么内层循环**跨外圈的总迭代次数 ≤ 上界**，于是

```
外圈 n 次 × (每圈常数 + 内层总次数 n / 外圈次数)  →  O(n) 而不是 O(n²)
```

**实现代价**：中。需要
- 在 `bound.py` 里给"内层循环"记一个**跨外圈累计的计数器**（现在每个循环独立计数）；
- 一个"计数器单调"的判定（`_only_grows_init` 已经有了——这一轮为 `while (j < hi)` 写过，**可复用**）；
- κ 合成时把内层的贡献记成 **`O(上界)` 一次**，而不是 `O(圈数 × 每圈)`。

**风险**：判错就会给出比真实小的界（**破界**）。**所以必须保守**：任何一条不满足 → 退回现在的乘积口径。

**收益**：KMP、单调栈、双指针、滑动窗口——**算法库里最常见的一批**，全部从"只能写二次"变成"能写线性"。

## 2 第二类：数据结构不变式（**很难修**）

### 现象

有些上界**不来自循环形状，而来自数据结构自己维护的不变式**：

| 结构 | 不变式 | 由此得出的上界 |
|---|---|---|
**并查集（按秩合并）** | 秩小的树挂到秩大的树下 ⇒ 树高 ≤ log₂n | 单次 `find` = `O(log n)` |
**AVL / 红黑树** | 高度差 / 黑高约束 ⇒ 高 ≤ 2log n | 查找 `O(log n)` |
**哈希表** | 装载因子 ≤ 1 ⇒ 期望桶长 `O(1)` | 查找 `O(1)`（**期望**，不是最坏） |
**跳表** | 层数 = 期望 log n（随机） | 查找（**期望**，模型外） |

### 实测代价

```text
并查集 find：κ = 53n + 63（把 while 追根记成 n 圈）
  写 O(log n)（数学上真）→ ▲ 超标，比值 1.46×10¹²
  写 O(n)                → ✓ 达成（诚实但松 40 倍以上）
```

**注意**：这里的 `O(log n)` **不是摊还**——按秩合并单独就给单次最坏 `log n`。**工具推不出，是因为 `κ` 根本不知道 `rank[]` 是什么。**

### 能不能修

**能做的只有很窄的一格**：**让作者把不变式声明出来**。

```text
// 假想的语法
invariant  rank[r] ≤ rank[parent[r]]      // 或
invariant  height(tree) ≤ log2(size(tree))
```

工具据此把 `while (parent[r] != r)` 的圈数从 `n` 收紧成 `log n`。

**但这等于要工具做「不变式的静态验证」**——那是程序验证的范畴：

- 要证明每处修改都不破坏不变式（`union` 里两行）；
- 要证明循环在不变式下收敛（`find` 的 `r = parent[r]` 单调上升）；
- **一旦某个不变式证不出来，就得退 ⊤**，否则松紧两边都会错。

**代价：大，而且是开放式的**（每个不变式都要一条专门的证明规则）。**收益：小**——受影响的是并查集、平衡树这几类，**而这几类本来就可以改用内建容器**（`map`/`set` 就是 AVL，用户不用自己写）。

**结论：不做。**

---

## 3 建议

| 类 | 做不做 | 理由 |
|---|---|---|
**内层循环总次数有界** | **做** | 规则窄（三条判据）、影响大（KMP/单调栈/双指针全覆盖）、**可复用已有的 `_only_grows_init`** |
**数据结构不变式** | **不做** | 等于做程序验证；受益的结构用户可以直接用内建容器 |
**跨调用摊还** | **不做** | 模型之外（只承诺单次最坏上界） |
**期望复杂度** | **不做** | 同上；随机化结构本来就没有最坏 `log n` |

## 4 如果不做，怎么缓解

**一条原则：松是可以的，只要用户知道自己松在哪。**

1. **`W-Target-Loose`**（已有）：静态判断"κ 里有一大块是不随 n 增长的常数"，提示"改 κ 这一侧，别放宽 target"；
2. **`tools/tightness_compare.py`**（已有）：给出 `κ ÷ ops` 的实测比值，**并按"比值是否随 n 发散"区分「阶真的错了」与「常数项太松」**；
3. **本文**：说明"为什么松"，让用户知道**这是分析器的边界，不是自己写错了**；
4. **不催作者写紧**：松的界永远是安全的，**判据不该逼人写它算不出来的东西**。

---

## 5 一句话

**界松有两个来源：**「内层循环被当成了乘积」（**可修，值得修**）和「数据结构的不变式推不出」（**不修，改用内建容器**）。
**跨调用摊还和期望复杂度都不在这个问题里——它们是模型之外，不是缺陷。**

## 7 CSAPP 说的三个「编译器没法优化」，我们能改几个

CSAPP 第 5 章：C 有三类东西挡住优化。**我们因为已经有契约，多数可以从契约自动生成提示。**

> ⚠ **这一节是设计与路线，不是现状**（2026-11-11 核对）：
> 仓库里**没有**任何 `[[gnu::const]]` / `__restrict` / `__attribute__` 的生成代码
> （`grep -r 'gnu::' src/` 为空），也没有后端。下表第三列写的是**「机制上可以怎么用」**，
> 落地状态见"状态"一列。

| 障碍 | C++ 里的解法 | **我们的解法** | 状态 |
|---|---|---|---|
| **别名**（`xp`/`yp` 可能同一块） | `restrict`（承诺 + UB）、局部拷贝、传值、`const T&` | **值语义天然无别名**；损失被限制在「签名里有指针的函数」上 | ✅ 值语义已落地；`__restrict` 生成**未做** |
| **函数调用**（编译器假设调用能改一切） | `static inline`、`-flto`、`__attribute__((pure/const))`、`noexcept`——**几乎要人手写** | **`effects` 自动生成属性**：`effects {}` → `[[gnu::const]]`；只读全局 → `[[gnu::pure]]`；无 throws → `noexcept`；体积小 → `inline` | 🔴 **未做**（无后端、无属性生成） |
| **圈数未知** | `#pragma unroll N`（靠猜）、**PGO**（两阶段构建） | **`sizes` 声明**（= 声明式 PGO）+ **`?!` 的实测阈值**（可以扩展到循环版本化） | 🟡 `sizes` 与 `?!` 已落地；**循环版本化未做** |

### 7.1 三条我一度说成「做不到」，其实都有语言层解法

| 障碍 | 我原话 | **准确说法** | 代价 |
|---|---|---|---|
| 输入驱动的运行时界 | 只能靠 PGO | **`sizes` 声明 + `?!` 阈值 → 循环版本化** | 代码膨胀 |
| 指针形参的 `restrict` | 我们证不出 | **`requires distinct(p, q)` + debug 断言**——把 C 的「无声 UB」变成「可检查的前置条件」 | 少量运行期检查 |
| 跨函数别名 | 需要 LTO | **借用规则（Rust 式）**：`&mut` 独占 ⇒ 不别名是**类型规则的推论**，不需要全程序分析 | **写法受限、与 C++ 不一致** |

### 7.2 真正只能靠外部工具的，只有一条

**「哪个循环是热点」**——PGO 能给，我们只能靠 `ops` 的离线计数。**它不是 profile，只是计数。**

### 7.3 一句话

> **C++ 里这三样都要人手工写提示，写错了还不报错；我们的契约里有同样的信息，理论上可以自动生成。**
> **「契约驱动优化」的具体形状是：`.tu` 不只是文档，它是给编译器的输入。**
>
> **但别把"理论上"读成"已经"**：这一节三行里只有 `sizes` 与 `?!` 今天真的落地，
> 属性生成与循环版本化都还没有代码（上面那张表的状态列就是干这个用的）。

### 7.4 借用规则：不用 LTO 就能证明不别名（**提案；opt-in**）

> **这是提案，不是现状**：今天 `f(xs, xs)` 传两个可变别名**能过 check**（实测，2026-11-11）。
> 下面写的是"如果要做，规则长什么样、代价是什么"。

#### 规则本身（三条，缺一不可）

```
① 任一时刻，一个值只有两种状态：
     多个共享借用（const T&）—— 只读，可以有好几个
     或 恰好一个独占借用（T&）—— 读写，只能有一个
   两者不能同时存在。
② 借用活着的时间 = 从创建到最后一次使用（不是到作用域结束）。
③ 被独占借用期间，原值不能直接读写。
```

非法：`f(&x, &x)`（两个独占借用同一对象）、`h(&x, &mut x)`（共享与独占共存）、
`sort_in_place(&xs); print(xs.size());`（借用未结束就直读）。
合法：`f(&x, &y)`、`g(&x, &x)`（两个只读，允许）、`f(&s.a, &s.b)`（不同字段）。

#### 为什么它等于「签名自带 `restrict`」（关键在调用点）

```
f 的签名是 f(p: T&, q: T&)
→ 调用方要把同一个 x 传两次，必须先拿到两个独占借用
→ 规则 ① 禁止
→ 所以 p 与 q 一定指向不同对象
```

**这个推理只用了「`f` 的签名」+「调用方本地的借用状态」——都是本地的，不需要全程序分析，也不需要 LTO。**
Rust 拿到「不别名」不是分析出来的，是**类型规则排除掉的**。

**换来的东西**：

```cpp
// C++ 语义：编译器必须假设 xp == yp
void twiddle(long* xp, long* yp) { *xp += *yp; *xp += *yp; }   // 2 载入 2 存
// 规则成立后：生成 T& __restrict，编译器可以合成 1 载入 1 存
```

**而且 `__restrict` 是「证明了才发」，不是让作者拍胸脯。**
`const T&` **不需要** restrict——多个只读借用即便别名，读也不会互相失效。

#### 三条代价（给具体写法，不说形容词）

**① 写法受限——会拒绝这些 C++ 写法**

| 写法 | C++ | 规则成立后 |
|---|---|---|
| `swap(x, x)` | 合法无害 | **✗ 拒绝**（两个独占借用同一对象） |
| `copy(dst, src)` 传同一对象 | 合法（结果未定义但常被容忍） | **✗ 拒绝** |
| `f(&x); print(x);` | 合法 | ✗ 拒绝（借用横跨打印） |
| `f(&s.a, &s.b)` | 合法 | ✓ 允许（不同字段不别名） |
| 方法里 `&mut self` + 同时借 `self.field` | 合法 | ✗ 拒绝 |

**真正被禁的是「同时」持有，不是「先后」**——`f(&x)` 之后再读 `x`，借用已结束，可以放行（NLL）。

**② 现有代码大面积变红**

```
17 个样例 + 138 个测试文件 + 全部教学文档都要复核
→ 已经能通过的代码可能变红（一次迁移）
→ 迁移后要重新冻结 golden（κ 没变，但「什么是合法程序」变了）
→ 文档里"怎么写"的示例要重排（教学成本）
```

**这不是修几个 bug，是改一条语言规则。保守估计一到两天迁移 + 一轮全面复核。**

**③ 与 C++ 的「看起来一样」冲突 —— 这条是决定性的**

**产品目标是「C++ 改名即用」，而 C++ 允许别名**（`swap(x, x)`、`f(&v, &v)`）。
**规则一旦强制，这些代码改名后直接报错。**

#### 结论：**opt-in，不做默认**

```
默认  →  与 C++ 一致（允许别名）→ codegen 不发 __restrict
可选  →  .tu 里写 strict borrows;  或函数级 requires distinct(p, q);
         → 检查变严 + codegen 发 __restrict
```

**与其它机制同一哲学**：`sizes` / `?!` / `guarantees` 全是 opt-in。**强制性借用规则会让「改名即用」直接破产；opt-in 则让愿意付代价的人拿到优化。**

**落地清单**：

```
① .tu 语法：strict borrows;  /  requires distinct(p, q);
② typecheck：只在声明了 strict 的模块里做借用检查
③ codegen：只在 proven 的情形发 __restrict
④ 诊断：E-Borrow-Conflict / E-Borrow-ExclusiveWithShared，
        消息提示"本模块声明了 strict borrows；要允许别名就去掉它"
⑤ 文档：能力边界新增一节，明确"默认允许别名，strict 是 opt-in"
```
