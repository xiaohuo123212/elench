# `parallel` 的计账：**判阶 max、总量 Σ、墙钟是估计**

> 规格 §13.6 B-24 一句话：**`parallel` 的 κ 是各任务之和，判阶等价于取最大**。
> 本文说清工具链现在**怎么把这两条都直接给出**，以及**大小核**为什么只能进
> "墙钟估计"、不能进 κ。
>
> 对应实现：`src/cost_domain/par.py`（视图与估计）、`symbolic.Cost.par`（节点）、
> `cost_check._profile`（判阶）。

## 1. 三个数，性质不同，别混

`cost` 遇到 `parallel` 会多打一段"最大核视图"。它把三件事**分开**写：

```
parallel：4 任务（判阶 max / 总量 Σ；核数与权重**不进 κ**）
  任务0  κ = n(xs)×7                       阶 n
  任务1  κ = n(xs)×7                       阶 n
  任务2  κ = n(xs)×7                       阶 n
  任务3  κ = n(xs)×7                       阶 n
  瓶颈 = 任务0（阶相同 → 取 n=1048576 处取值最大者）
  判阶 κ = n(xs)×7    ← 只取它的**阶**（B-24，机器无关）
  总量   = Σ = n(xs)×7 + n(xs)×7 + n(xs)×7 + n(xs)×7    ← B-24 的 Σ 口径（allocation 同此）
  wall_est = 15928.9（profile：4 核 [P×1, P×1, E×0.45, E×0.45]，at n=1024；**估计，不是契约**）
```

| 这一列 | 是什么 | 依赖机器吗 | 是契约吗 |
|---|---|---|---|
| 每个任务的 `κ` | 该任务自己的成本式 | 不 | 是（组成 κ） |
| **判阶 κ** | `max_i 阶(κ_i)` | **不** | **是**（`target` 按它判） |
| **总量 Σ** | `Σ_i κ_i` | **不** | 是（`allocation` 同口径） |
| **`wall_est`** | 这台机器上跑完的**估计** | **是**（核数 + 权重） | **不是** |

**为什么 `wall_est` 不能进 κ**：κ 要能**跨机器冻结**（`tests/golden/kappa.json`
就是冻结产物）。核数一进 κ，同一份源码在两台机器上就有两个 κ，契约不再可审计。
规格 B-27 也把"需要核数"推到了**将来**的精确成本目标（`work: { max: N }`）。

## 2. 没有机器档时：同构，核数 = 任务数

不给 `--cores` 时，默认档是"**同构，每个任务一个核**"（`weight` 全 1）。
于是

```
wall_est = max_i κ_i
```

——正好是"每个任务各占一个核"的墙钟，也是唯一不需要额外假设的那个数。
κ 与它无关；换档只改这一行。

## 3. 机器档（大小核）：一个 JSON

```json
{
  "note": "2 大核 + 2 小核",
  "cores": [
    { "kind": "P", "weight": 1.0 },
    { "kind": "P", "weight": 1.0 },
    { "kind": "E", "weight": 0.45 },
    { "kind": "E", "weight": 0.45 }
  ]
}
```

```bash
elench cost my_mod --cores=machine.json --at=1024
```

- `weight` 是**速度因子**：同一份工作，权重 `w` 的核耗时 `1/w`。**只有比值有意义**
  （`1.0 : 0.45`），单位怎么定都行。
- 也接受裸数组 `[1.0, 1.0, 0.45, 0.45]`（数字当权重，`kind` 记作 `C`）。
- `--at=N` 把每个尺寸量都设成 `N`，用来给 `wall_est` 一个规模。
  **κ 全是常数时不用给**；κ 含尺寸量又没给 `--at` 时，工具打
  `wall_est = —`，**不替你猜一个规模**（猜出来的数字会被当成承诺）。
- 档坏了（缺 `weight`、权重 ≤ 0）→ **退出码 2 并说明**，不会静默当同构。

## 4. 核数 < 任务数时怎么放：LPT

规则一句话：**任务按成本从大到小，逐个放到"当前预计完成最早"的核上**。

```
任务降序；对每个任务 j = argmin_核 ( 已分工作量 / 该核权重 )
同分 → 取权重更大者；再同 → 取下标更小者（完全确定）
```

理由三条：

1. **它把"核数 ≥ 任务数"定义成了同一个算法的退化情形**：一开始核都是空的，
   最重的任务落到最快的核，于是每个任务各占一个核、`wall = max_i κ_i / w_i`
   ——没有"另一种情况"要单独解释。
2. **从不空转**：只要还有任务，就一定被放到某个核上；不会出现"核闲着、
   任务却排队"这种明显不优的估计。
3. **对同构核有已知质量**：LPT 的 makespan `≤ (4/3 − 1/(3m))·OPT`，
   估计不会离谱地乐观。**异核（大小核）下这个保证不成立**——所以它只是估计。

**任务不拆**：`parallel` 的任务是语义单位（B-23：任务集合静态可见），
把一个任务切两半放到两个核上已经不是同一个程序了。

## 5. 退化情形

| 情形 | 行为 |
|---|---|
| **1 个任务** | κ 里仍是 `par(κ₁)`（保留"这里写过 parallel"），判阶 = `阶(κ₁)`，总量 = `κ₁`，`wall = κ₁ / w` |
| **0 个任务**（空块） | κ = `0` |
| **嵌套 `parallel`** | 视图按层深缩进列出每个块；外层把内层那个任务整体当**一个**任务（阶 = 内层各任务的 max，仍是 max 的 max） |
| **某个任务是 ⊤** | 整块 **⊤**（Σ 与 max 都不知道；折成 ⊤ 才能让既有的"⊤ 吸收"继续生效） |
| **任务里有 `?!`** | 该任务的 κ 是分段的（`piece`），整块判阶时**任一分量判不了 → 整块判不了**（不跳过它取已知分量的 max——那个未知的可能更大） |

## 6. 机读版

`--json` 的每个函数多一个 `parallel` 段（只在 κ 里真的有 `par` 时出现）：

```json
{
  "size_variable": "xs",
  "blocks": [
    {
      "index": 0,
      "depth": 0,
      "n_tasks": 4,
      "occurrences": 1,
      "needs_scale": true,
      "tasks": [
        { "index": 0, "cost_expression": "n(xs)×7", "order": [1, 0],
          "order_text": "n", "value_at_ref_scale": 7340032.0 }
      ],
      "bottleneck": 0,
      "bottleneck_by": "order",
      "judge_expression": "n(xs)×7",
      "total_expression": "n(xs)×7 + n(xs)×7 + n(xs)×7 + n(xs)×7",
      "ref_scale": 1048576,
      "profile": "4 核 [P×1, P×1, E×0.45, E×0.45]",
      "profile_default": false,
      "at": 1024,
      "wall_estimate": 15928.888888888889,
      "wall_note": null
    }
  ]
}
```

- `order` 是 `(多项式次数, log 因子数)`——与 `target` 判定用的是**同一份**判阶逻辑。
- `value_at_ref_scale` 是在 `ref_scale`（`2^20`）处的取值，只用来**同阶比大小**
  （“谁更重”），不是承诺。
- `profile_default = true` 表示没给 `--cores`（同构、核数 = 任务数）。

## 7. κ 里的 `par` 节点

`symbolic.Cost` 多了一种节点：

```
par(κ₁, …, κₙ)
```

| 运算 | 结果 |
|---|---|
| `value` / `evaluate` | **Σ**（工作量；与改前的 κ 逐字同值） |
| `order` / `_profile` | **max**（B-24；与"Σ 的阶"恒等） |
| `add(par, c)` / `mul(n, par)` / `max(par, x)` | 当普通节点，不特判：外层加减乘除的阶仍是 max 口径（乘法的次数相加） |
| `render` | `par(…)`——**不压平成一个和**（压平了就回到"拿不到瓶颈任务"的老问题） |
| `to_dict` | `{"operator": "parallel", "order": "maximum", "value": "sum", …}` |

```elench
u64 four(const vector<u64>& xs) {
    u64 a = 0;
    u64 b = 0;
    parallel {
        { for (u64 i = 0; i < xs.size(); i = i + 1) { a = a + 1; } }
        { for (u64 i = 0; i < xs.size(); i = i + 1) { b = b + 1; } }
    }
    return a + b;
}
```

上面这段的 κ 是 `… + par(2 + n(xs)×17 + 17, 2 + n(xs)×17 + 17) + …`：
**判阶是 `n`**（不是 `n²`），**总量是两者相加**。`allocation` 维度同样取 Σ，
且并行块里的分配**不再漏记**（2026-11-09 修：以前 `parallel` 里的分配一律记 0）。
