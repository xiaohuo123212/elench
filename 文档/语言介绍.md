# AI 导向编程语言 —— 介绍

**版本**：对应规格 v0.66
**一句话**：**把「我想让它多快」从注释里搬到编译器能查的地方。**

---

## 一、它要解决的两件事

### ① AI 写得出来，但核不了

AI 生成的代码"能跑"是常态，"有多快"没人答得上。

**性能信息今天只活在三个地方**：注释里、PR 描述里、作者脑子里。**编译器一个都不看。**

于是最常见的场景是：

```cpp
// O(n log n)   ← 这句谁写的？对不对？没人查
std::vector<int> f(const std::vector<int>& xs);
```

### ② 常数因子只能靠猜

同一个问题有几种写法，选哪个取决于输入规模：

| 去重方式 | 什么时候快 |
|---|---|
| 哈希集 | n 大、重复率高 |
| 排序后扫描 | n 小、内存紧 |
| 位图 | 值域小而稠密 |

**AI 猜不出临界点在哪。** 它不是不努力，是**这件事本来就不可推断**——要测。

## 二、六个机制

### 1. 意图与事实分开

| 概念 | 谁写 | 是什么 |
|---|---|---|
| **`target`** | **人**（AI 提议，批准后冻结） | **意图**：我希望多快 |
| **`cost`** | **编译器** | **事实**：实际多快 |

```
spec evaluate(text: Vec<u8>) -> i64! {
    effects    {alloc};
    requires   text.length() <= MAX_TOKENS;

    target {
        time      : { max: O(text.length()) },
        allocation: { max: O(text.length()) },
    };
}
```

编译器算出实际成本，写进 `evaluate.cost.yaml`：

```yaml
functions:
  evaluate:                    # ▲ 本次有变化
    time:        {min: "n",   max: "n"}
    allocation:  {min: "0",   max: "8*n"}
    debt:        {time: none, allocation: none}
```

**关键**：`cost` 不是人填的。
**让 AI 写 `cost`，等于让被考的人自己报分。**

**实际超过目标 → 记为「债务」**，留在表里，不许抹掉。

---

### 2. 声明与实现分家

一个模块是两份文件：

```
calculator.tu       ← 全部声明：签名、effects、target、model、requires
calculator.eln       ← 只有签名 + 函数体，零声明
```

**为什么分**：

| 理由 | 说明 |
|---|---|
| 人能通读 | `.tu` 只有几十行，人**真的会看完**并签字 |
| 谎言集中 | **7 处可撒谎的东西全部在 `.tu`；`.eln` 里一处都没有** |
| 各司其职 | 人审 `.tu`，AI 写 `.eln` |

**代价**：签名写两遍，不一致会报错（`E-Spec-SigMismatch`）。

---

### 3. 算法选择外包给测量

**不让你猜常数因子，让你列举候选。**

**在 `.tu` 里**：候选是真实的函数，`over` 名单即声明；候选没有自己的 `spec`，契约由宿主给出（宿主签名见 `样例/search.tu`）。

<!-- @include 设计/目前设计/样例/search.tu#choose -->
```
    choose search_impl(const Vec<u64>& xs, u64 key) -> u64! {
        over {
            search_linear,
            search_binary,
            search_interp pending
        }
        ;
        objective time;
    };
```
<!-- @end -->

**在 `.eln` 里**：决策点就标在那一行（片段；完整 `func` 见 `样例/search.eln`）。

```
pub func binary_search(xs: Vec<u64>, key: u64) -> u64! {
    …
    const idx = ?!search_impl(xs, key);      // ← 只有这一步交给测量
}
```

**`?!`：问号表示"未定"，叹号表示"确定要选一个，只是还没量"。**

| 概念 | 谁定 |
|---|---|
| 有哪些候选、在什么输入上比什么 | **AI** |
| 具体选哪个 | **测量** |
| 要不要接受这张表 | **人 / 门禁** |

**两条硬规则**：

- **`?!` 不能是整个函数体**（`E-Choose-WholeBody`）——那叫用测量代替设计
- **`?!` 的成本取所有候选的上界**——**故意倒逼**：想混一个 O(n²) 的候选进来，数学上做不到

---

### 4. 骨架先行

**AI 的正常工作方式是先搭骨架、再填细节。** 语言承认这一点：

```
    choose search_impl(xs: Vec<u64>, key: u64) -> u64! {
        over      {search_linear, search_binary, search_interp pending};   // ← 声明：这个还没写
        …
    }
```

| 命令 | 含未实现时 |
|---|---|
| `elench check` | **通过**（骨架合法、可审） |
| `elench build` | **失败**（不能测量没写的候选） |

**为什么必须显式声明**：检查器能算出"谁没写"，但**算不出"这是故意的还是漏的"**。

**写完一块就能量一块**：

```
$ elench bench search_binary
判定: search_linear 慢 12%（超过噪声地板 3%）
可信度: 低（隔离测量）
```

---

### 5. 每个可能出错的地方留痕

| 设计 | 规则 |
|---|---|
| **算术返回 `Result`** | `(a + b)?` —— 每个可能溢出的点必须写 `?` |
| **文本是字节** | `Vec<u8>`，一个元素一个字节 |
| **没有隐式转换** | `u64` 与 `i64` 混算必须显式 |
| **没有类型后缀** | `42u64` 是错的，写 `42` |
| **一种写法** | 长写法 `function` 是**错误**，不是兼容形式 |
| **块只由 `}` 收尾** | v0.68 起不写 `end`；条件 MUST 带括号 |

**这些都不"优雅"，但它们让每处决策都得写出来。**

---

### 6. 报告告诉你「哪些数字不能全信」

每份成本报告有独立的**信任区**：

```
信任区
├─ target（人批准，冻结）        影响：契约是否成立
├─ repeats（声明，不可验证）      影响：循环成本上限
├─ model（声明，不可验证）        影响：测量取点
└─ external 块（登记即信任）      影响：全链路成本
```

**共 7 处。** 报告还会把「算出来的」与「派生的」分开列——**一个转发点不算一次独立验证**。

## 三、一个完整例子

**任务**：在一个**有序**数组里找 `key` 的下标，找不到返回 `NotFound`。四步里只有"用哪种查找"这一步是未定的。

**声明部分（`search.tu`）**：

<!-- @include 设计/目前设计/样例/search.tu#spec -->
```
error SearchError;

// 二分查找的循环条件。
// 循环体里区间每次至少减半，所以圈数上界是 log2(区间长度)——这是算法性质，
// 无法由条件形态推出（规格 T13 来源①），只能由谓词的 repeats 声明（来源②）。
spec in_range(u64 lo, u64 hi) -> bool {
    effects { };
    repeats log(hi - lo);
}

spec binary_search(
    const Vec<u64>& xs, u64 key) -> u64! {
    effects { alloc };
    requires is_sorted(xs);

    benchmodel {
        data {
            xs = sorted_u64s();
            key = any_of(xs);
        }
        scale {
            xs in range(1, 1048576, *2);
        }
        seed = 1;
    };

    target {
        time: { max: O(log(xs.length())) },
        allocation: { max: 0 },
    }
    ;

    choose search_impl(const Vec<u64>& xs, u64 key) -> u64! {
        over {
            search_linear,
            search_binary,
            search_interp pending
        }
        ;
        objective time;
    };
}
```
<!-- @end -->

**实现部分（`search.eln`）**：

<!-- @include 设计/目前设计/样例/search.eln#fn -->
```
// `in_range` 是普通函数：spec 在 .tu 里（含 repeats），实现就在这里。
// 它只被用作 while 条件——区间未空就继续。
func in_range(u64 lo, u64 hi) -> bool {
    return lo < hi;
}

pub func binary_search(
    const Vec<u64>& xs, u64 key) -> u64! {
    const u64 n = xs.length();
    if (n == 0) {
        return Err(SearchError::NotFound);
    }
    const u64 idx = (?!search_impl(xs, key))?;
    return idx;
} kernels search_impl(
    const Vec<u64>& xs, u64 key) -> u64! {
    search_linear {
        u64 i = 0;
        while (i < n) {
            if (xs.at(i) == key) {
                return i;
            }
            i = i + 1;
        }
        return Err(SearchError::NotFound);
    }
    search_binary {
        u64 lo = 0;
        u64 hi = n;
        while (in_range(lo, hi)) {
            const u64 mid = lo + ((hi - lo) / 2)?;
            const u64 v = xs.at(mid);
            if (v == key) {
                return mid;
            }
            if (v < key) {
                lo = mid + 1;
            } else {
                hi = mid;
            }
        }
        return Err(SearchError::NotFound);
    }
}
```
<!-- @end -->

**注意两件事**：

- **候选没有 `spec`**——它的契约由宿主给出，不重复写
- **`binary_search` 四步里只有一步是 `?!`**——其余逻辑照常由作者负责

## 四、与其他语言的关系

| 语言 | 它做什么 | 我们不同在哪 |
|---|---|---|
| **C++** | 通用系统语言 | 我们**不追求通用**；不替代 C++ |
| **Rust** | 内存安全 + 零开销 | 我们**语义跟 Rust**（移动、借用），但多了**成本契约**这一层 |
| **Dafny / F\*** | 全功能验证 | 我们**不做完整验证**——只做**有界**的成本与效果检查 |
| **Zig** | 显式优于隐式 | 同源，但我们**把"多快"也纳入显式** |

**我们不做什么**：

- 不自研后端（用冻结版本的通用后端）
- 不承诺"精确时间"，只承诺**量级 + 结构上界**
- 不做"发现更优算法"（那不可强制）
- v0 不做代码生成、不做契约**验证**（只出报告）
