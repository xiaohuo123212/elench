## 0. 为什么有这份文档

2026-11 早期做过一轮「把真实第三方库 pull 下来，看能不能被 Elench 吃下去」的探针。
那批材料放在 `build/real-libs/`，而 **`build/` 是 gitignored 的**——结论只存在于本机，
换机器或清 `build/` 就没了。这份文档是把当时的**实测记录**固定下来，同时给出复现方法。

## 3. 复现方法

```bash
# 前提：build/real-libs/ 还在（gitignored，不在仓库里）
cd <仓库根>

# 单个探针
python -B src/dsh.py check build/real-libs/_cases/stb2.eln --compat
python -B src/dsh.py cost  build/real-libs/_cases/stb2.eln --compat
python -B src/dsh.py cpp   build/real-libs/_cases/stb2.eln --compat

# 37 个探针一起重跑（脚本已入库）
python -B tools/probe_real_libs.py            # 移植口径（内联 include）
python -B tools/probe_real_libs.py --ffi      # FFI 口径（不内联，与当年日志同一口径）
python -B tools/probe_real_libs.py --json     # 机读
```

`tools/probe_real_libs.py` 用**同一份输入文件**（`_probe/eln/*.eln` 与 `_cases/*.eln`），
不修改它们，只跑 `check` / `cost` 并汇总。**它不替代人工判断**：`check` 通过不等于
"这个库能用"，只等于"这一份探针的语法/类型/契约检查过了"。

## 4.5 2026-11-23 重跑（当时的日志 → 现在的代码）

用 `tools/probe_real_libs.py` 跑同一批 37 个探针（**输入一个字没改**）：

| 诊断码 | 探针数 | 说明 |
|---|---|---|

`E-Parse-UnexpectedTop` | 4 | 顶层形状没认出来 |
`E-Parse-Expected` | 3 | 同上 |

## 4.6 第二轮：尖括号 include 与 `#warning`（2026-11-23）

针对 §4.5 的 17 条 `E-Lex-IncludeUnresolved`，做了两件事：

1. **第 19 条扩展到尖括号形式**：`#include <nlohmann/json.hpp>` 也按搜索路径找，

## 4.7 「17 条 IncludeUnresolved 为什么没降」——查清了

上一节把这条标成**未验证**。现在查清了，而且是一行代码的问题：

**实测**（`f1_include_only.eln`，搜索路径已设）：

```
✗ E-Lex-IncludeUnresolved @3005:1  `#include "core.h"`：本语言不读头文件…
```

行号 3005 在 `fmt/core.h` **内部**——它自己写着 `#include "core.h"`（用基名包含自己）。
我们的内联器把这个文件当"已经内联过"跳过，但**把这一行留在了正文里**；下游看到
`#include "core.h"` 就报未解析。

**修法**：已内联过的 include 直接**丢掉**（那正是 `#pragma once` / include guard 的语义）。

**修后**：`E-Lex-IncludeUnresolved` 从 17 条降到 4 条（只剩 doctest 那 4 个探针，
它们的 `doctest.h` 确实不在搜索路径里）。**通过数仍是 9/37**——因为卡点整体往下移了：

| 诊断码 | 探针数 |
|---|---|
`E-Parse-UnexpectedTop` | 16 |
`E-Keyword-LongForm` | 13 |
`E-Lex-MacroUnsupported` / `MacroUnterminated` / `E-Lex-Preprocessor` | 13 各 |
`E-Parse-SkippedBody` | 13 |
`E-Parse-Expected` | 10 |
`E-Struct-NoGeneric` | 8 |

**下一步（按数据）**：`E-Keyword-LongForm`（13）看起来是访问说明符 `public:` 被
namespace 展平后落到顶层；`E-Lex-Macro*`（13）是宏机制（`##` 拼接、函数宏边界）。

## 4.8 一次**失败的尝试**（记下来，免得下次重走）

按 §4.7 的频次，下一个目标是 `E-Keyword-LongForm`（13 个探针）。实测其中第一条是：

```
✗ E-Keyword-LongForm @7434:3  `mutable` 应写作 `mut`
```

我的推断是"成员函数解析那条路把 `mutable` 拒了"，于是在 struct 成员循环里加了一条
"`mutable` / `volatile` / `inline` / `constexpr` 在 `--compat` 下跳过"。

**结果：无效。** 合成用例 `struct P { mutable u64 a; }` 仍然报：

```
✗ E-Keyword-LongForm @2:5  `mutable` 应写作 `mut`
```

说明 `mutable` 的拒绝点**不在这条路上**（更可能在**字段**解析或更底层的长格式关键字表）。
那条改动已经**撤回**（留着就是死代码 + 说谎的注释）。

**所以这一轮的净产出是"这个方向不对"**，不是修复。`E-Keyword-LongForm` / `mutable`
的真实拒绝位置**仍未定位**——下一轮第一件事是从 `E-Keyword-LongForm` 的抛出处往上追。

## 4.9 `mutable` 定位成功（第 22 条）

§4.8 记录了一次失败的尝试：在 parser 的成员循环里跳过 `mutable` **无效**。
这一轮往上追，发现**根因在词法器**——`mutable` 是 `LONG_FORM_HINT` 里的长写法词，
词法阶段就报了 `E-Keyword-LongForm`，parser 根本没机会看到它。

**修法（两层，缺一不可）**：

1. `lexer.py`：`--compat` 下 `mutable` / `volatile` / `inline` / `constexpr` 不再当长写法错误；
2. `parser.py`：struct 成员循环跳过这四个词（无节点、不影响 κ）。

**实测**：

```
struct P { mutable u64 a; inline u64 get() { return a; } };
→ check --compat：✓ 通过（2 个函数）
→ 不带 --compat：✗ E-Keyword-LongForm（严格模式不变）
```

**但 37 个探针仍是 9/37**——`fmt` 的探针在这一层之后还有 `E-Lex-BadEscape` /
`E-Lex-MacroUnsupported` 等宏与字面量机制挡着。这一条修的是**真库里的普遍写法**，
不是"让 fmt 通过"。

前几轮的脚本只跑 `_probe/eln/` 与 `_cases/*.eln`，**漏了 `_cases/eln/`**——而有历史日志的
那 4 个探针的正本（`utf8.eln` / `xxh.eln` / `stb.eln` / `stb2.eln`）正好在那里。
脚本已补上。用**同一份原始输入**重跑，结果与日志**对不上**：

|---|---|---|
`_cases/eln/utf8.eln` | **exit=0 通过** | exit=1（`E-Lex-PreprocessorError`、`E-Parse-Expected`） |
`_cases/eln/xxh.eln` | **exit=0 通过** | exit=1（`E-Keyword-Unsupported`、`E-Lex-MacroUnsupported`） |
`_cases/eln/stb2.eln` | **exit=0 通过** | exit=1（同上报错） |
`_cases/eln/stb.eln` | exit=1 | exit=1 |

复现命令（与脚本一致，搜索路径 = 9 个库的 `include/` 与库根）：

## 4.11 §4.10 的疑问查清了：**不是回归，是口径变了**（并已可复现）

§4.10 说"日志 exit=0，今天 exit=1，不知是回归还是环境"。查清了，两条证据：

**证据一**：在 `cf77cfe`（探针入库那次）上跑同一个 `utf8.eln` → `rc=0`。
**证据二**：把 include 的处理退回**第 19 条之前的口径**（整行丢掉、不报错）→ 4 个探针全对上：

| 探针 | 日志 | 今天的对照（老口径） |
|---|---|---|
`utf8.eln` | exit=0 | **rc=0 ✓** |
`xxh.eln` | exit=0 | **rc=0 ✓** |
`stb2.eln` | exit=0 | **rc=0 ✓** |
`stb.eln` | exit=1 | **rc=1 ✓**（`E-Call-Undeclared`，与日志同） |

**结论**：当年那批探针是 **FFI 风格**（`extern … from "lib"` + `link "lib"`），
`.eln` 里的 `#include` 只给 C 侧 shim 用，对本语言没有语义。那时 include 被**整行忽略**，
所以 check 能过。第 19 条把它改成"内联 / 找不到就报错"——对普通移植是进步，对这批探针是退步。

**处理**（不是回退第 19 条，是给出口）：新增开关

```bash
ELENCH_NO_INCLUDE_INLINE=1   # include 整行忽略，回到第 19 条之前的口径
```

默认行为**不变**（内联 / 报错）。测 FFI 风格探针时打开它，才是在比同一件事。

**所以"当年跑通了"是真的**，只是那个"通"是在 include 被忽略的口径下——这一点以前没写，
现在写清楚了。

## 6. 已知缺口（当时就有的）

- **stb 的动态数组宏**（`stbds_arrput` 之类）：宏展开出的调用，本语言没有宏系统 →
  `E-Call-Undeclared`。不是拼写映射能解决的。
- **`cpp` 出码**：那 4 个探针全 exit=1，原因当时没查。**未知**。
