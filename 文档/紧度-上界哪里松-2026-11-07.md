## 1. 多算（一）：内层循环按 `n` 算，实际只跑一半

**症状**：两个 O(n²) 样例的比值是 **2.47 / 3.46**，而同类 O(n) 样例都在 1.1–1.4。

**数据**（`max_pair_sum` @ n=64）：

```
κ 的内层项      n(xs) × n(xs) × 24 = 64 × 64 × 24 = 98,304
实测总数                                          41,387
内层真实迭代次数        64 × 63 / 2 = 2,016
实际每次迭代 ≈ 41,387 / 2,016 ≈ 20.5 个操作
```

**根因**：内层是

```text
while (i < n) {
    u64 j = i + 1;        // ← 起点是 i+1
    while (j < n) { … }
}
```

而 κ 把**内层每次外层迭代都按 `n` 次**算（64×64 = 4,096），实际是 `n - i - 1`，
总和 `n(n-1)/2 ≈ 2,016`。**恰好高估一倍。**

**这是全项目 O(n²) 样例的系统性偏差**，不是某个样例的毛病。
**修法（在 `bound.py`）**：识别内层循环变量的**初值形如 `i + c` / `i`**，
把内层上界记成 `n - i`（乘下去自然得到 `n²/2`）。
**杠杆**：所有 O(n²) 样例的比值从 ~2.5–3.5 掉到 ~1.2–1.7。

## 2. 多算（二）：`?!` 没有分档表 → 承诺取 `max(各候选)`

**数据**（`search` @ n=64）：

```
κ ≤ 12 + … + max(2 + n(xs)×18 + 18 + 3,   ← 线性候选 search_linear
                  4 + log2(n(xs))×37 + 37 + 3)  ← 二分候选 search_binary
实测 186（跑的是二分那一路）
```

`max(线性, 对数)` 在 n 大时**等于线性** → 承诺是 O(n)，而实际 O(log n) → 比值 12.73。

**这不是 bug**：没有表时"承诺取最大"是保守且正确的语义（工具不知道运行期会选哪条）。
**但它是当前最大的松。** 修法不是改界，而是**给表**：
`dsh measure` 产出 `.dispatch.yaml` 后，承诺变成**分段**，每段取该段真正会跑的候选。

**同一类**：`topk`（8.02×，堆法 vs 反复扫描，两候选阶差大）。

**这里值得写进文档的一句话**：
> **`?!` 的紧度不是"算"出来的，是"测"出来的。** 不给表，工具只能给你最坏候选的上界。

## 3. 看不出来：实测根本没按 n 跑

`calculator` / `lcs` / `matmul` 在 n=64 下实测只有 **67 / 23 / 12** 个操作。

**说明**：这三个函数的**工作量不是由"尺寸 n"决定的**——

- `calculator`：输入是一段**表达式文本**，随机文本立刻报错返回；
- `lcs` / `matmul`：参数是**多个维度**（`a.length()×b.length()` / `dim³`），
  而 `measure_one(prog, n)` 只把**一个**规模量设成 n，其余按最小规模造。

**所以它们的比值没有意义**（`holds=True` 只说明"实测 ≤ κ"，没说明"界紧"）。

**这是"看不出来"的两类**：
1. **数据相关早退**（calculator）：实测取决于输入内容，不取决于 n；
2. **多参数尺寸**（lcs/matmul）：现有的"按 n 定一个尺寸"的测量方式**覆盖不到**。

**修法方向**：让测量能指定**每个尺寸量各自的值**（`--size xs=64 --size ys=64`），
否则多参数样例永远只能"看起来紧"而无法验证。

## 4. 常数偏高（小头）

单循环样例普遍 1.35–1.76。`max_pair_sum` 的 `--explain` 显示内层每次迭代记 **24**，
而实测约 **20.5**——**每个迭代多算 ~17%**。

`--explain` 的「杠杆」一栏已经能定位到具体项（99.9% 的贡献来自内层项），
所以这项**不是靠猜**，是能逐项看的。

## 5. 结论：按杠杆排序

| # | 松在哪 | 影响 | 修法 | 代价 |
|---|---|---|---|---|
| **1** | 内层循环按 `n` 而非 `n - i` | **所有 O(n²) 样例 ×2** | `bound.py` 识别内层初值 | 半天 |
| **2** | `?!` 无表 → `max` | `search` 12.7×、`topk` 8× | **给表**（已有 `measure`） | 需真测 |
| **3** | 每迭代常数 24 vs 20.5 | 所有样例 +17% | 逐项对账 `--explain` | 1 天 |
| **4** | 多参数尺寸测不了 | lcs / matmul **验证不了** | 测量支持逐尺寸赋值 | 半天 |

**第 1 条最值**：一处改动，所有二次样例的紧度直接减半，而且**不改语义**（只是把已知的初值用上）。

## 6. 第 1 条：查清了，但**便宜的路走不通**（2026-11-07 实查）

### 现状链路（读代码得到的，不是猜）

1. 内层 `j < n` 的内层循环 的条件推导给出 `Bound("sub", left=n, right=j)` —— **这一步是对的**；
2. 但 `src/cost_domain/cost_interp.py` 的 `bound_to_cost_inst` 里：

   ```text
   if k == "sub":
       return go(x.left)     # a - b <= a     ← 就是这里
   ```

   **`sub` 直接退化成左边**（注释写明是"保守"：`a−b ≤ a`）。所以 `n − j` 变成 `n`。

### 为什么不能简单"把 sub 实现出来"

即便把 `sub` 变成真的减法：
- 内层界是**每次外层迭代**的界（最坏是 `n−1`，当 `i=0`）；
- 总迭代次数 = `Σ_{i=0}^{n−1} (n−i−1) = n(n−1)/2`；
- **要拿到 `n²/2`，需要"对计数器求和"的推理**，而当前引擎只有「上界 × 体成本」，
  没有 Σ。**没有 Σ，`sub` 实现了也只是 `n×(n−1)` ≈ `n²`，几乎没有收益。**

### 所以真正的修法（本次没做）

要么给 Cost 增加一种「三角和」形态（`tri(n) = n(n−1)/2`），
要么让循环成本计算支持对已知计数器区间求和。

**两条都要动 `Cost` 的渲染 / 求值 / 比较三处**——而比较那一处正是"达成/债务/无法判定"
三值判定的核心。**在没把这条链读透之前动它，风险是让 κ 低估**（那是"说错"，比松严重）。

### 结论

**第 1 条挂起**，理由记在这里，不是"没时间"，是**代价与风险不匹配当前收益**：
- 收益：二次样例 κ÷实测 2.47/3.46 → 约 1.25/1.7；
- 风险：碰到三值判定的比较逻辑；
- 替代路径：**第 2 条（给 `?!` 表）收益更大且不动界**（`search` 12.7×、`topk` 8×）。

**建议先做第 2 条。**

## 8. **更正**：`search` 的 12.73× 是我比错了口径（2026-11-07 晚）

### 错在哪

第 0 节的表用的是 `kappa_vs_measured.measure_one(...)`，它比的是
**最坏上界 κ vs 典型实测**。而 `search` 一找到 key 就 `return`——
**典型输入下它几乎不跑完整个数组**。

**所以 12.73× 不是界松，是"典型"比"最坏"便宜。**

### 正确的数（走 `export`/`tightness_table`，它会搜最坏输入）

| n | κ | 实测（最坏） | κ÷实测 |
|---|---|---|---|
| 32 | 1,216 | 466 | 2.61 |
| 64 | 2,368 | **900** | **2.63** |
| 128 | **624** | **257** | **2.43** |
| 256 | 698 | 292 | 2.39 |
| 512 | 772 | 327 | 2.36 |

**两个结论**：

1. **分档表本来就在生效**：n=64→128 时 κ 从 **2,368 掉到 624**（线性段 → 二分段）。
   **承诺早就是分段的**，不缺表。
2. 真实比值 **2.36–2.63**，而且**随 n 缓慢下降**（2.63 → 2.36）——**阶是对的**。

### 剩下的松是常数，不是阶

- 线性臂：κ 记 **18 / 元素**，实测 **900/64 ≈ 14** → 高估约 1.3×；
- 二分臂：κ 记 **37 / 次对数迭代**，实测 **257/7 ≈ 37** → **基本吻合**。

所以 `search` 的剩余空间只有 **~1.3×**，不是 12.7×。

### 两个测量口径必须分开说（这条要写进文档）

| 口径 | 谁在用 | 比的是 |
|---|---|---|
| **典型** | `kappa_vs_measured` / `bench_suite` | κ vs 典型输入 |
| **最坏** | `export` / `tightness_table` | κ vs 搜到的最坏输入 |

**拿"典型"的比值说"界松"是错的** —— 对提前退出（`return` 在循环里）的函数尤其错。
这也是工具自己的「判读」那句话的意思：*「相对典型」大而「相对最坏」小 ⇒ 界其实很紧，只是日常输入便宜。*

## 11. **更正 + 查清**：`lcs` / `matmul` 的"看不出来"不是多尺寸问题

第 3 节我说"`measure_one` 只把一个尺寸量设成 n，其余按最小规模造" —— **这句是错的**。
回读代码：`kappa_vs_measured` 的回落路径对**每个容器参数**都按 n 造
（`make_u8s(seed, n)` / `random_u64s(seed, n)`）。所以 `lcs(a, b)` 两个都是长度 n。

真正的原因是**夹具不满足函数自己的前提**。

### `lcs`：界其实**很紧**，只是撞了自己的上限

| n | κ | 实测 | κ÷实测 |
|---|---|---|---|
| 8 | 5,270 | 3,928 | 1.34 |
| 16 | 18,486 | 15,624 | 1.18 |
| 32 | 69,110 | 62,404 | 1.11 |
| **61** | 243,081 | 226,683 | **1.07** |
| 64 | 267,126 | **23** | 无意义 |

n≥64 时 `(n+1)² > LCS_CAP(4096)` → 函数**立刻 return**（23 步）。
**所以 lcs 的界在它自己的有效区间内是 1.07 —— 全项目最紧的几个之一。**

### `matmul`：参数之间有约束，夹具不满足它

`matmul(a, b, dim)` 一上来就检查 `a.length() == dim*dim`。
而夹具按 `a.len = b.len = n`、`dim = max(2, n//4)` 造 —— 于是 `dim² = n²/16 ≠ n`，
**大多数 n 直接 `DimensionMismatch` 返回（12 步）**。

| n | κ | 实测 | 说明 |
|---|---|---|---|
| 8 | 1,036 | **12** | dim=2, need=4 ≠ 8 → 早退 |
| **16** | 4,286 | **2,064** | dim=4, need=16 = 16 ✓ **唯一成立的一档** |
| 32 | 23,458 | **12** | dim=8, need=64 ≠ 32 → 早退 |

**n=16 处 κ÷实测 = 2.08**。

## 12. 所以第 6 条真正缺的是什么

**不是"逐参数赋值"，是"派生尺寸"**：让某个参数的长度由其它尺寸量**算出来**
（`a.length = dim × dim`）。现在的 `benchmodel.data` 只会给"长度 = 当前规模"或字面量，
表达不了 `dim²`。

### 本次已做的（小步，向后兼容）

`src/bench.py::make_args` 现在认得 `sized[p] = <正数>` 表示**该参数用显式尺寸**，
`0` 仍是"跟随当前规模"。这为"派生尺寸"留了接口，但**还不能表达 `dim²`**。

### 建议的下一步（没做）

在 `.tu` 的 `benchmodel.data` 里允许**尺寸表达式**，例如
`a = random_u64s(dim * dim)`；实现上只需把生成器的 `n` 从一个整数换成
"用其它参数求值"的表达式。**这会同时解决 `matmul`，以及将来所有"二维缓冲"的样例。**
