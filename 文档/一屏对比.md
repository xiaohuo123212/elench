# 一屏对比：同一件事，两种做法

**这页只说一件事**：把「性能承诺」写进语言，和只写在注释里，差在哪。

---

## 任务

求一个字节数组的平均值。**求和有两种写法，复杂度相同，快慢取决于机器。**

---

## 用本语言

<!-- @include 设计/目前设计/样例/sum.tu#spec -->
```
error CalcError;

spec average(
    const Vec<u8>& scores) -> u64! {
    effects { alloc };
    requires scores.length() > 0;

    benchmodel {
        data {
            scores = make_u8s();
        }
        scale {
            scores in range(1, 1048576, *2);
        }
        seed = 1;
    };

    target { time: { max: O(scores.length()) }, allocation: { max: 0 }, };

    choose sum_kernel(const Vec<u8>& scores) -> u64! {
        over {
            sum_by_index,
            sum_by_iter
        }
        ;
        objective time;
    };
}
```

<!-- @include 设计/目前设计/样例/sum.eln#fn -->
```
pub func average(
    const Vec<u8>& scores) -> u64! {
    const u64 n = scores.length();
    if (n == 0) {
        return Err(CalcError::Empty);
    }
    const u64 total = (?!sum_kernel(scores))?;
    return total / n;
} kernels sum_kernel(
    const Vec<u8>& scores) -> u64! {
    sum_by_index {
        u64 s = 0;
        u64 i = 0;
        while (i < n) {
            s = s + scores.at(i);
            i = i + 1;
        }
        return s;
    }
    sum_by_iter {
        u64 s = 0;
        for (x in scores) {
            s = s + x;
        }
        return s;
    }
}
```

## 用 Rust

```rust
// 复杂度只能写在这里，编译器不看、测试不查、CI 不知道
/// O(n)
pub func average(scores: const Vec<u8>&) -> Result<u64, CalcError> {
    if scores.is_empty() { return Err(CalcError::Empty); }
    const total = sum_by_index(scores);        // ← 选哪个？作者猜的
    Ok(total / scores.len() as u64)
}

func sum_by_index(xs: const Vec<u8>&) -> u64 { … }
func sum_by_iter(xs: const Vec<u8>&) -> u64 { xs.iter().map(|&b| b as u64).sum() }
```


| 问题 | Rust 的答案 |
|---|---|
| 哪个更快，选哪个？ | **人工看图**，然后手改代码 |
| 换台机器还快吗？ | 不知道，**没人重跑** |
| 这个函数现在还是 O(n) 吗？ | 靠人读代码 |
| 有人改慢了怎么办？ | CI 跑不跑 bench，取决于你配没配 |

## 逐条对比

| | 本语言 | Rust + criterion |
|---|---|---|
| **承诺写在哪** | `target` 子句，人批准后冻结 | 注释 |
| **实际成本从哪来** | **编译器算**（不可撒谎） | 没人算 |
| **谁保证没退化** | `cost ≤ target` 自动比对，差记为债务 | 人看 bench 报告 |
| **语言知道有多个实现吗** | **知道**（`choose` + `?`） | 不知道，只是两个普通函数 |
| **bench harness** | 由工具按调用点生成 | 手写 |
| **选哪个** | 测量决定，写成**可审的分档表** | 人工改代码 |
| **切换点在构建时变吗** | **不变**（表冻结，改了要显式刷新） | 编译期没有切换点 |
| **测错了会怎样** | **程序仍然正确，只是慢**（定理 T-7） | 可能选错，也可能退化 |

---

## 为什么选「求和」做这个对比

**因为两个候选的复杂度完全一样（都是 O(n)）。**

**这恰好逼出核心问题**：

> **成本模型看不出差别，CI 的复杂度检查也看不出差别——只能测。**
> **所以"语言知道有这两个实现"这件事，才是关键。**

如果换成"哈希 vs 排序"（不同阶），读者会以为我们在做"复杂度比较"，
**那反而落回老套**，而且那种情况下人一眼就能看出，不需要工具。

---

## 我们不做什么（这一节必须留着）

| 不做 | 说明 |
|---|---|
| 不证明"哪个更快" | 测量是统计，不是证明；差异低于噪声地板时明确返回 `inconclusive` |
| 不证明"这个算法最优" | 发现更优算法是不可强制的（规格 §11.5） |
| 不保证"常数因子" | 只承诺量级 + 结构上界（K2） |
| 不替代 profiler | 我们测的是**候选之间**，不是整个程序的瓶颈 |

> **一句话**：**Rust 让你"能测"，本语言让你"必须测，而且测完有记录"。**
