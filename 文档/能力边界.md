# 能力边界：Elench 能写什么、写不了什么

> **一句话**：这是一门**做成本契约**的语言，**不追求通用、不替代 C++**（[介绍](介绍.md) §4「写不了什么」）。
> 它能把排序、查找、DP、位运算、文件/JSON 写清楚并给出**上界**；它**写不了**模板、继承、异常、`goto`、lambda、变长参数、128 位整数，也**表达不了**摊还界与真指数。
> **指针（2026-11-10 更新）**：`T*` / `&x` / `*p` / `p->f` / `nullptr` 的**语法与类型已经支持**（§2.2.6），
> **运行期也已接线**（2026-11-10）：`&x` 产出地址、`*p` 读写那块存储、`p->f` 同一条路、`nullptr` 解引用报
`E-Pointer-NullDeref`（**不崩宿主**）。`E-Pointer-RuntimeUnsupported` 已退役。
>
> 每条结论都带 **实测报错原文** 或 **文档出处**——没有出处的句子不写在这里。
> 同一件事怎么写：看 [语法清单](语法清单.md)；110 个内建：看 [内建函数](内建函数.md)；与 Rust/C++ 的关系：看 [介绍](介绍.md) §5。
> 想自己复核（30 秒一条）：§6 给了探针方法。

**最后更新**：2026-11-11　**实测环境**：Windows / Python 3.14 / HEAD `6320c2f`（`p40-work`）　**取证**：每条都在临时目录里跑过 `elench check` / `elench run`，探针见 §6

## 0. 先读这一段：**"没报错" 不等于 "能写"**

死语法和缺失能力最难发现的**不是报错，而是"试了才知道"**。更糟的是有一类写法**根本不报错**：`check` 绿、`run` 也跑得动，只是**做的不是你写的那件事**。

### 0.1 四个反例（都实测过，原文照抄）

**"没报错"**分两种：一种是**以前**不报（已修，见 §2.1.1），一种是**今天仍然不报**。
下面四条都是**今天**的行为：

| 你以为会被拒绝的写法 | 实际发生 | 它其实是什么 |
|---|---|---|
| `u64 x = -1;` | **`check` ✓，`run` 得 `18446744073709551615`** | 整数隐式转换 + 回绕（静默） |
| `u8 b = 300;` | **`check` ✓，`run` 得 `44`** | 赋值时按位宽截断（静默） |
| `#define N 10` 后 `#if N > 5` | **`check` ✓，走的是 `#else`** | `#if` 里不做宏展开，`N` 认不出 → 判假 |
| `f(xs, xs)`（`f` 收两个 `vector<u64>&`） | **`check` ✓，`run` 真改同一个对象** | 完整借用规则还没落地（§2.2.6 之后） |

机理是三条规则叠在一起：

1. **整数之间允许隐式转换**（只有浮点→整数被拒），且按位宽静默回绕；
2. **`#if` 只看"定义集"，不做宏展开**——写 `#if defined(N)` 才对；
3. **借用检查只做了"`const` 形参被改写"这一层**，独占/共享的冲突还没查。

> **所以本文的口径是：`check` 通过只是必要条件，每个"能写"都跑过 `run`。**
>
> 另外三条**以前**会静默通过、**2026-11-10 起明确报错**的写法
> （`goto done;`、`u64 y = &x;`、`u128 x;`），原文留档在 §2.1.1。

### 0.2 三条判据（下面三节就是按它分的）

| 判据 | 含义 | 典型证据 | 你该做什么 |
|---|---|---|---|
| **A 设计如此** | **不会补** | 干净的 `E-Parse-*` / `E-Lex-*`；或（更糟）静默通过 | 换写法（§4） |
| **B 还没做** | 可以补，只是没排到 | `E-Call-Undeclared` / `E-Type-UnimplementedContainer` | 换写法；要补就去改 `src/` |
| **C 契约表达不了** | 是 `Cost` 的边界，不是语法 | `E-Target-BadForm` / 判 `⊤` / 记债务 | 把 target 松一档，并在注释里说清为什么 |

### 0.3 一条容易搞错的口径：内建到底几个

**110 个内建 = 100 个注册在 `src/stdlib.py`（`stdlib.FNS`）+ 10 个由解释器直接实现**
（`print` / `sort` / `sort_by` / `map` / `filter` / `fold` / `count_if` / `min` / `max` /
`for_each`）。出处：[内建函数](内建函数.md) 开头的口径行；`stdlib.FNS` 的键数实测 `100`。

**数学函数现在有了**（2026-11-10，§2.2.1）：`sqrt` / `log2` / `floor` / `ceil` /
`round` / `fabs` / `abs` / `popcount` / `clz` / `ctz` 全部 `O(1)`、不分配。
**仍然没有**的是 `sin` / `cos` / `tan` / `exp` / 自然对数 `log` / `pow` 内建
（幂是**运算符** `**`，`x ** 0.5` 就是平方根）、以及 128 位整数。

### 1.2 一个最小可跑骨架（实测 `add_one(41) = 42`）

`a.tu`：

```elench
spec add_one(u64 n) -> u64 {
    target { time: { max: O(1) }, };
}
```

`a.eln`：

```elench
u64 add_one(u64 n) {
    return n + 1;
}
```

```bash
$ python -B src/elench.py check a
✓ 通过（1 个函数，其中 0 个无体）
$ python -B src/elench.py run a --fn=add_one --u64=41
42
```

**两件必须记住的事**：`.tu` 是**人签的契约**（`spec` / `target` / `effects` / `external`），`.eln` 只有函数实现、没有任何声明（[语法清单](语法清单.md) §1）。函数只写 C++ 形状 `u64 add_one(u64 n) { … }`；`func add_one(u64 n) -> u64` 已下线（`E-Func-KeywordRemoved`）。

### 1.2.1 一个 C++ 程序改文件名就能跑（R1，2026-11-10）

**产品目标**：*一个 C++ 程序只需要把文件名改成 `.eln`，就成为 Elench 程序。*
R1 落地的是**语法面四件事**；语义面（lambda / 继承 / 模板）不在解释器里实现，
那些只走 C++ 路径。**指针是例外（2026-11-10）**：语法与类型已经接上，
运行期已接线（§2.2.6）——`run` 可以直接跑指针代码；解引用 `nullptr` 报 `E-Pointer-NullDeref`。

| C++ 写法 | 现在能不能写 | 说明 |
|---|---|---|
| `#include <vector>` / `#include "x.h"` | **标准头**：接受、整行忽略；**非标准头**：`E-Lex-IncludeUnresolved`（2026-11-13 起，此前静默） | 内建类型与门面头已覆盖标准库；第三方头**我们不读**，所以必须明说——否则「check 通过」是假的 |
| `#pragma once` / 其它 `#pragma` | ✅ 接受、整行忽略 | 编译期提示，与语义无关 |
| `#define N 10` / 函数式宏 `#define SQR(x) ((x)*(x))` | ✅ **先预处理再分析**（2026-11-10）：展开后建 AST，κ 算在展开后的程序上 | 实测 `#define N 10` 后 `print(N)` 打 `10`、`SQR(3)` 打 `9` |
| `#if` / `#ifdef` / `#undef` | ✅ 接受；按定义集求值，未定义的为假 | ⚠ **`#if` 里不做宏展开**：`#define N 10` 之后 `#if N > 5` 判**假**（`N` 认不出）。要写 `#if defined(N)` 或字面量比较 |
| `using namespace std;`（文件顶部或函数内） | ✅ 接受 | 写了才**允许短名**（规格定稿）；R1 里短名与 `std::` 都接受（见下） |
| `std::vector<u64>` / `std::map<u64,u64>` / `std::optional<T>` | ✅ 与短名**同一个类型** | `.tu` 写 `vector<u64>`、`.eln` 写 `std::vector<u64>` 也判同一个签名（不再 `E-Spec-SigMismatch`） |
| `std::expected<T,E>` | ✅ 归一成 `expected<T,E>` | `T!` 糖与 `?` 不变 |
| `std::string s = "hi";` | ✅ 归一成 `vector<u8>` | 这正是 `Text` 的运行时形态（`Text` 这个名字本身不是类型名，写它报 `E-Type-Unknown`）；`s.size()` / `print` 都能用 |
| `std::pair<K,V>` | ❌ `E-Type-NoPair` | 名字认得、语义没接（R2 的 `m.insert({k,v})` 一起做）；两元组写 `(K, V)` |
| `int main() { … }` / `auto f() -> T` | ✅ 函数声明不再必需 `func` | `auto` 只用于**后置返回**；`auto x = 1;` 仍报「没有类型推断」 |
| `const u64& x` 形参 | ✅ 只读借用 | 以前 `E-Ref-Scalar` 连 `const` 一起拒（C++ 最常用的形参写法！）；现在 `const` 形参放行，**可写的** `u64& x` 仍拒（标量写不回调用方） |

#### 类型映射表（**方案甲：整数一律 64 位**）

| C++ 拼写 | 映射到 | 备注 |
|---|---|---|
| `int` / `signed` / `signed int` | `i64` | **64 位**，不是 32 位 |
| `unsigned` / `unsigned int` | `u64` | |
| `short` / `short int` | `i64` | |
| `unsigned short` | `u64` | |
| `long` / `long int` / `long long` / `long long int` | `i64` | Windows 的 `long` 是 32 位，这里也是 64 位 |
| `unsigned long` / `unsigned long long` | `u64` | |
| `char` | `u8` | 字符就是字节；`'a'` 的类型是 `u8`（`E-Type-NoChar` 已退役） |
| `signed char` / `unsigned char` | `i8` / `u8` | |
| `bool` | `bool` | |
| `float` / `double` / `long double` | `f32` / `f64` / `f64` | |
| `size_t` / `uintptr_t` | `u64` | |
| `ssize_t` / `ptrdiff_t` / `intptr_t` | `i64` | |
| `int8_t` / `int16_t` / `int32_t` / `int64_t` | `i8` / `i16` / `i32` / `i64` | **按位宽精确**（定长名是"我就是要 N 位"的表达） |
| `uint8_t` … `uint64_t` | `u8` … `u64` | 同上 |

#### ⚠ 溢出语义差异（**这是"静默不同"的高危点，必须知道**）

- **`int` 在这里是 64 位**。C++ 的 `int` 是 32 位：`int x = 2147483647; x = x + 1;`
  在 C++ 里是**有符号溢出（UB）**，在这里得到 `2147483648`（`i64`，不溢出）。
  凡是**依赖 32 位回绕**的程序（哈希、校验和、位运算技巧）行为会不同。
- **写 `uint32_t` / `int32_t` 就按 32 位回绕**（`u32` 是 `UInt` 子类，每次运算都取
  模 2^32）。所以"我确实要 32 位"时，用**定长名**，不要用 `unsigned int`。
- **无符号的差异最危险**：`unsigned` 的 32 位回绕在 C++ 里是**有定义**的，映射到
  `u64` 就变成"不回绕"。所以 `unsigned` 只承诺「名字认」，不承诺 32 位回绕。
- **有符号的差异落在 C++ 的 UB 区间**：`int` / `long` / `short` 的溢出 C++ 不保证，
  映射到 64 位属于"实现自选"，但仍请按上面的建议用定长名表达真实意图。
- `i8` / `i16` / `i32` 在**赋值 / 返回 / 入容器**时按位宽回绕，**中间表达式**仍按
  64 位算（`i32 a = 2147483647; a + 1` 在表达式里不溢出，赋回 `i32` 才回绕）。

### 1.3 契约能写成什么样（`target` 里的成本式）

| 你想要的阶 | 写法 | 实测 |
|---|---|---|
| 常数 | `1` / `O(1)` | ✓ |
| 线性 | `O(n)` / `xs.size()` | ✓ |
| `n log n` | `O(n * log(n))` | ✓ |
| 平方 | `O(n * n)` | ✓ **不能写 `O(n^2)`**（成本式里没有 `^`，`E-Target-BadForm`） |
| `√n` / `n^(2/3)` / `n^(3/2)` | `O(sqrt(n))` / `O(pow(n, 2/3))` / `O(pow(n, 3/2))` | ✓ |
| `n / log n` | `O(n / log(n))` | ✓ |
| `n log log n` | `O(n * log(log(n)))` | ✓ |

**注意 `sqrt` 在两个位置、两个意思**：`target` 的 `sqrt(x)` 是**成本代数里的函数名**（`x^(1/2)`，只判阶、不算值）；`.eln` 函数体里的 `sqrt(16.0)` 是**内建**，返回 `4.0`（§2.2.1）。

## 2. 写不了什么（核心）

### 2.1 判据 A：设计如此（**不会补**）

| 写法 | 实测（首个错误，原文） | 替代 |
|---|---|---|
| `new` / `delete`（手动内存管理） | `E-Keyword-Unsupported`（`new Foo(1);` / `delete p;`） | 容器自己管理内存；指针可以指到已有对象（`T* p = &x;`，§2.2.6），但**不做堆分配** |
| `template<…>` | `E-Parse-UnexpectedTop … 这里不该出现 'ident'` / `E-Keyword-Unsupported`（`template`） | 泛型写在名字后：`T pick<T>(T a, T b)` |
| 宏系统（`#define` 目前是**预处理展开**，不是宏系统） | 宏展开落在 AST 之前，`#if` 里不做宏展开（见 §1.2.1） | `const` + 具名函数 |
| 继承 / `virtual` | `E-Parse-UnexpectedTop … 这里不该出现 'ident'`；`struct D : B` → `E-Parse-Expected … 期望 ';'，实际是 ':'` | `enum` + `match`、函数表 |
| 异常 `throw` / `try` | `E-Parse-Expected … 期望 ';'，实际是 'int'` / `… 实际是 '{'` | `expected<T, E>`（`T!` + `?`） |
| `goto` + 标签 | `E-Keyword-Unsupported`（**2026-11-10 起**；以前 `goto done;` 静默变成 `var-decl`） | 早返回 / `for` + `break` |
| lambda / 闭包 `\|x\| { }` | `E-Parse-ExpectedExpr … 期望表达式，实际是 '\|'` | 具名函数 + `fold/map/sort_by` |
| 用户可变参数 `u64... args` | `E-Parse-Expected … 期望 ')'，实际是 '..'` | `vector<u64>` 打包 |
| `u128` / 大整数 | 类型名本身 → `E-Type-Unknown`（**2026-11-10 起**；以前静默当 `UNKNOWN`）；字面量超界 → `E-Lex-IntOverflow` | 两条 `u64` 拼 hi/lo |
| SIMD `f32x4` | `E-Type-Assign … 声明为 f32x4，初值是 i64` | 标量循环 |
| 原子 / 互斥 `atomic<u64>` | `E-Type-Assign … 声明为 atomic<u64>，初值是 i64` | `parallel { }`；真并发走 FFI |

#### 2.1.1 三格**以前**会静默通过（2026-11-10 已改成明确报错）

它们不是"报错"，是"绿着做别的事"——**当时只有 `run` 才能发现**。现在三格都
在 `check` 阶段报错，下面同时给出**旧行为**（为什么危险）和**现在的诊断**。

**① `goto done;` —— 以前被当成变量声明**

```text
$ elench parse goto.eln        # 2026-11-10 之前的 AST
var-decl done = {'mut': True, 'has_init': False}   @2:5
  type-name goto   @2:5
```

`goto` 不是关键字：`goto done;` 满足「标识符 + 标识符 + `;`」，被声明解析吃掉，
`check` 零诊断、`run` 正常返回。现在 `goto`（和标签 `done:`）报：

```text
✗ E-Keyword-Unsupported @1:26  [.eln] 本语言没有 `goto`：跳转用 `while` / `break` /
  `continue` / `return`。（`goto` 不是关键字——以前 `goto done;` 会被静默解析成
  变量声明「类型名 goto、变量名 done」，什么也不做。）
```

**② `&x` / `*x` —— 以前是恒等**

```text
$ elench parse ref.eln         # 2026-11-10 之前的 AST
var-decl y = {'mut': True, 'has_init': True}   @3:5
  type-name u64   @3:5
  ref   @3:13
    path x   @3:14
```

`ref` / `deref` 是前缀表达式节点，运行期直接返回操作数的值（`u64 y = &x;` 得 `1`）。
**当时它们不是取地址/解引用**——语言里没有地址这回事。**2026-11-10 起指针成为
语言的一部分**（§2.2.6），判据改成**按类型**（`*`）与**按位置**（`&`）：

| 写法 | 结论（2026-11-10 起） |
|---|---|
| `f(&a)`，被调方该形参是 `T&` / `const T&`，且 `a` 是变量/下标/字段 | ✅ 接受：**显式借用标记**（等价于不写 `&`；样例 `calculator.eln` 的 `apply_top(& values, & operators)` 属于这一格） |
| `f(&a)`，该形参是 `T*` / `const T*` | ✅ 接受：取地址得到指针实参 |
| `T* p = &x;` / `p = &x;` / 指针返回位置 | ✅ 接受：取地址的三种成立位置 |
| `print(&x)`（内建，不是引用/指针形参） | ❌ `E-Unary-Unsupported`（运行期 `&` 仍未接，不能把"地址"当值传出去） |
| `u64 y = &x;` / `&(1 + 2)` | ❌ `E-Unary-Unsupported`：取地址的结果是**指针**，不能给标量；`&` 只能作用于位置 |
| `*p`（操作数是 `T*` / `const T*`） | ✅ **解引用**（结果类型是 `T`；成本 `O(1)`） |
| `*x`（操作数是标量 / 容器 / struct / 引用） | ❌ `E-Unary-Unsupported`——`*` 只对指针成立（这条按**类型**判，不再一律拒绝） |
| `a * b`（二元乘法）/ `a & b`（按位与） | 不受影响（走 `BINARY` 表，不经过前缀分支） |
| **局部**声明 `vector<u64>& r = ys;` | ❌ `E-Ref-Local`：本语言没有局部引用 / 别名；以前静默变成**拷贝**（`r[0] = 9` 改不到 `ys`）。引用只存在于**形参位置** |
| **标量 / 枚举 / 元组的引用形参** `void bump(u64& x)` | ❌ `E-Ref-Scalar`：解释器里引用能用 = 值本身是可变对象（容器 / struct）；标量是不可变值，`x = 42` **写不回调用方**（以前静默如此）。要写回就返回新值、返回 `expected`，或用 `vector<u64>& out` 承载输出。**`const u64& x`（只读借用）不报**——R1 起，C++ 最常用的形参写法必须能用 |
| 容器 / struct 的引用形参 `vector<u64>&` / `Point&` | ✅ 真写回（容器元素 / struct 字段都能传出去） |

**③ `u128` —— 以前当 `UNKNOWN` 类型名**

以前 `u128 x = 1;` 报的是 `E-Type-Assign 声明为 u128，初值是 i64`（消息把读者
引到"初值类型不对"，而真正的病因是**没有 u128 这个类型**）；更宽的洞是
`u128 x;` / `foo_t x;`（**无初值**）——**零诊断**。现在两处都报：

```text
✗ E-Type-Unknown @1:26  未知类型名 `u128`：本语言没有这个类型。标量写
  u8/u16/u32/u64/i8/i16/i32/i64/f32/f64/bool；容器写 vector/array/map/set/optional；
  自定义类型要在 .tu 里用 struct / enum / error 声明。
```

`as` 的目标类型也是类型位置：`u64 y = 0 as u128;` 同样只报 `E-Type-Unknown`，
不再报「初值是 u128」。对照：`f32` 是**真类型**（不报）；`size_t` / `uint32_t` /
`char` / `int` 也是**真类型**（R1 起归一成宽度类型，不报）。

真正装不下的**字面量**才报 `E-Lex-IntOverflow`：

```text
✗ E-Lex-IntOverflow @2:13  [.eln] 整数字面量超出 u64 范围：18446744073709551616（u64 最大 18446744073709551615）。本语言没有比 u64 更宽的整数类型，也不会静默按 2^64 回绕
```

#### 2.1.2 为什么这些是"设计如此"

- 这门语言**不追求通用**（[介绍](介绍.md) §4.1「有意的缺口」、§4.2「还没做」）；
- 会**破坏 κ 确定性**的机制被主动删掉过：`spawn` / `asm` / `scope` 已于 2026-11-05 下线，理由是"并发下的时间不是确定上界""内联汇编的操作数不可数"（[语法清单](语法清单.md) §spawn/asm/scope 已下线）；
- **SIMD / 原子 / 手动内存管理（`new` / `delete`）**进不了"操作数 × 尺寸"这套代数。
  **指针是部分例外（2026-11-10）**：语法与类型已接、`*p` 成本记 `O(1)`，但
  **运行期已接线**（§2.2.6）；但指针**不能用来伪造堆分配**——`new` / `delete` 仍然拒绝。

#### 2.2.1 数学内建：**已经有了**（2026-11-10，一条刚过期不久的缺口）

这一节以前是"唯一的日常必撞缺口"：`sqrt` / `floor` / `ceil` / `abs` / `log2` /
`popcount` 一个都没有，而 **FFI 也补不上**——C ABI 后端不支持 `f64` 参数
（`E-FFI-Unsupported`）。现在这 10 个进了语言本体：

| 函数 | 签名 | 语义（**逐条按 C**） |
|---|---|---|
| `sqrt(x)` | `(f64) -> f64` | 负数 → **NaN**（不是错误、不是 0） |
| `log2(x)` | `(f64) -> f64` | `0.0 → -inf`、负数 → NaN |
| `floor(x)` / `ceil(x)` | `(f64) -> f64` | 返回 **f64**（不是 `u64`）；`inf`/`nan` 原样 |
| `round(x)` | `(f64) -> f64` | **`.5` 远离零**：`2.5 → 3.0`、`-2.5 → -3.0`（不是银行家舍入） |
| `fabs(x)` | `(f64) -> f64` | `-0.0 → 0.0` |
| `abs(x)` | `(T) -> T` | 跟实参类型走：无符号恒等、有符号取负、`f64` 同 `fabs` |
| `popcount(x)` | `(u64) -> u64` | 64 位里 1 的个数；`popcount(0) = 0` |
| `clz(x)` / `ctz(x)` | `(u64) -> u64` | 前导/末尾零个数；**`clz(0)` / `ctz(0)` 报错**（C 是 UB，本项目不编值） |

成本全部 **`O(1)`、不分配**：放进循环里，κ 只随圈数走。

```elench
f64 norm(const vector<f64>& xs) {
    f64 s = 0.0;
    for (const auto& x : xs) {
        s = s + sqrt(x * x);
    }
    return s;
}
```

实测（`run`）：

```text
sqrt 9.0   = 3.0        floor -3.7 = -4.0     ceil 3.2 = 4.0
round 2.5  = 3.0        round -2.5 = -3.0     fabs -1.5 = 1.5
log2 8.0   = 3.0        popcount 255 = 8      clz 1 = 63      ctz 8 = 3
clz 0      → ✗ InterpError: clz(0) 未定义（C 的 `__builtin_clz(0)` 是 UB）：先判空再取
```

**仍然没有**：`sin` / `cos` / `tan` / `exp` / `log`（自然对数）/ `pow` 内建
（幂用运算符 `**`）、128 位整数。要这些只能自己写（二分 / 级数），或者等它们
进语言本体——**FFI 不是出路**（`f64` 参数不支持）。

> ✅ **`**` 也是幂运算（2026-11-10 起）**：`x ** 0.5` 与 `sqrt(x)` 结果一致，
> 但 `sqrt` 是**内建**（成本记 `O(1)`、语义按 C）、`**` 是**运算符**（整数指数要求字面量）。
> 以前 `**` 是两个 `*`（右操作数被读成前缀 `*` 即"解引用"，运行期恒等），
> `2 ** 10` 静默得 `20`。现在 `**` 是独立 token、**右结合**、层次在 `* / %` 之上：
>
> | 写法 | 结果 |
> |---|---|
> | `2 ** 10` | `1024` |
> | `3 ** 4` | `81` |
> | `16.0 ** 0.5` | `4.0`（浮点幂） |
> | `2 ** 3 ** 2` | `512`（右结合：`2 ** (3 ** 2)`） |
>
> 类型层有两条明确拒绝：指数位置的字面量算不出（`E-Type-Pow-ExponentLiteral`）、
> 整数的指数是负字面量（`E-Type-Pow-NegativeExponent`）——都不会静默回绕。
> `a * b`（二元乘法）与 `a ** b` 是两条独立路径，互不影响。

#### 2.2.2 字符字面量：**已经有了**（一条常见的误传）

`'a'` 是**合法**的（规格 L18.1–L18.5），并且有一整套词法诊断：

| 写法 | 结果 |
|---|---|
| `u8 c = 'a';` | ✓ 实测 `run` → `97` |
| `''` | `E-CharLit-Empty … 空字符字面量；空字节请写 '\0'` |
| `'abcd'` | `E-CharLit-Multi … 字符字面量含多个码位` |
| `'\q'` | `E-CharLit-BadEscape … 不在封闭转义集内：\q。合法：\' \\ \n \t \r \0 \xNN` |

**`char` 类型 R1 起可以用**（归一成 `u8`，字符就是 `u8`，字符串就是 `vector<u8>`，[语法清单](语法清单.md) §3）：

```elench
u64 first_byte(const vector<u8>& s) {
    char c = s[0];      // R1 起合法；`c` 就是 u8
    u8   d = 'a';       // 等价（推荐写法：宽度显式）
    return c + d;
}
```

> 2026-11-10 之前 `char` 是**保留字**（词法器把 `char` 这个词当成"字符字面量"的 token 名），
> `char c = 'a';` 报 `E-Type-NoChar`。R1-A 把 `int` / `float` / `char` / `string`
> 四个词从关键字表里移除（它们是**字面量 token 的种类名**，不是关键字），
> 同一个词在**类型位置**映射到宽度类型。`char` 现在也能当普通标识符用（但别这么写）。

#### 2.2.3 运行期模块：`use` 只被**解析**

实测：

```text
// a.tu
use stdlib::text;
spec f(u64 n) -> u64 { target { time: { max: O(n) }, }; }
→ check ✓ 通过，run 正常（use 没有引入任何东西）
```

```text
// a.eln 里写 use
✗ E-Ai-HasUse @1:1  .eln 中不得出现 use（F-4/F-8）
```

**判据 B**：词法和语法都认 `use`，缺的是链接器（跨模块符号解析）。
现在唯一的"模块"是**同目录同名成对文件**（`a.tu` ↔ `a.eln`，[语法清单](语法清单.md) §1）。
替代：把代码拼进一个文件；真要调外部符号用 `extern … from "lib"` + `link` + `unsafe { }`。

#### 2.2.4 `deque<T>` 与 `heap`：容器没接线

```text
✗ E-Type-UnimplementedContainer @2:5  容器 `deque` 尚未实现：环形缓冲只在 `deque_new()` / `deque_push_*` 内建里，容器构造（`deque<T> d;` / `deque<T>::new()`）与方法（`d.push(1)`）没有接线。已实现的容器：vector / array / map / set / unordered_map / unordered_set / stack / queue。要两端增删，用 `vector` + 头尾两个索引。
```

注意这里的**分裂**：`deque_*` 这组**内建**能用（实测 `deque_new` / `deque_push_back` / `deque_len` → `2`），但 `deque<T>` **类型**被 `check` 直接拒绝。要两端增删，按报错说的做：`vector` + 头尾索引。

`heap` 从来没有过（[语法清单](语法清单.md) §容器支持现状："⬜ 未提供"）：用 `vector` + `swap` / `push_heap` / `pop_heap` 原语自己拼。

#### 2.2.5 JSON：能解析，但值类型要自己声明

`json_parse(text)` 现在静态返回 **`Json!`**（`expected<Json, Json>`，[内建函数](内建函数.md) §JSON 表），失败是 `Err(Json::*)`。
**它不是 `any` 了**（2026-11-10，K5：以前返回 `any` 意味着可以静默塞进 `u64`）——包装值必须
`?` 或 `match` 解包才能用。剩下的是**值类型**这一半：`Json` 要自己在 `.tu` 里声明
`enum Json { Null, Bool(u64), Num(u64), Str(vector<u8>), … }`，检查器才会按变体查字段。
不声明时 `Json j = json_parse(t)?;` 会报 `E-Type-Unknown`（类型名不存在），只能把它当包装值处理。
想静态：自己写 `enum Json { … }` 再手写解析（[语法清单](语法清单.md) §3 的枚举写法），或者只把 JSON 当"字节进、字节出"用 `json_emit_*` 拼。

#### 2.2.6 指针：唯一允许别名的地方（2026-11-10，**运行期已接线**）

> **一句话**：指针的**语法 / 类型 / 别名语义 / 运行期**都已按 C++ 立项
> （`T*`、`&x`、`*p`、`p->f`、`nullptr`）。`&x` 产出指向**那块存储**的地址，
> `*p` / `p->f` 读写都落到那块存储上，解引用空指针抛
> **`E-Pointer-NullDeref`**（运行期，与静态那条同名）——**不让宿主崩**。
>
> 接线之前这里挡着一道 `E-Pointer-RuntimeUnsupported`：那时解释器里
> `*p` / `&x` 是"值就是操作数本身"的旧语义，放行会**静默给错值**（比崩更糟）。
> 现在运行期真的接线了，那道闸**退役**（`src/typecheck.py` 的
> `_check_pointer_runtime` 只负责"未接时挡住"，接线后它没有存在理由——
> 该文件由另一路改指针消歧，那 4 行随它一起删）。

| 写法 | `check` | `run` | 说明 |
|---|---|---|---|
| `char** argv` | ✅ 通过 | ✅ 能跑（两层 `type-ptr`，`**argv` 双层解引用） | 两层 `type-ptr` |
| `const Json* p` | ✅ | ✅ | `const` 修饰**指向**，`p` 本身可改指向 |
| `Json* const p` | ✅（`p` 不可改指向，报 `E-Assign-Immutable`） | ✅ | `const` 修饰**指针** |
| `u64* p = nullptr;` | ✅ | ✅ | `nullptr` 只与指针兼容；`u64* p;` 的默认值也是空指针 |
| `u64* p = &x; u64 y = *p;` | ✅ | ✅ `y == 3` | `&` 取地址、`*` 解引用 |
| `*p = 7;` | ✅ | ✅ `x == 7`（写穿） | `deref` 是左值：走"改写"而不是"拷贝" |
| `q->field = 9;` | ✅ | ✅ `s.field == 9` | 与 `(*q).field` **同 AST**，不用单独接 |
| `if (p)` / `p != nullptr` | ✅ | ✅ | 指针可当条件；`nullptr` 是假值 |
| `*z`（`z` 是 `nullptr`） | ✅（可证时静态就拦） | ✅ 抛 `E-Pointer-NullDeref` | 运行期真的解引用时——**不崩宿主** |

**成本口径（三条，缺一条就得报错而不是猜）**

1. **解引用 = `O(1)`**：成本域对 `deref` 的分支是 `1 + Σ子表达式`
   （`src/cost_domain/cost_interp.py` 的 `_expr`），**不**因为"不知道指向多大的对象"
   退成 ⊤。遍历整条链时**迭代次数**才是变量。
2. **遍历上界必须来自声明的尺寸量**。本语言**没有新增 `alloc` 维度**：
   已有的 `allocation` 记的是"容器增长事件"（不是堆对象总数，见
   [语法清单](语法清单.md) §`allocation` 的口径），指针本身**不产生分配**
   （拷贝指针 = 拷贝地址，成本 0；跨容器/struct 的深拷贝表里没有指针这一项）。
   所以链式遍历的上界只能来自：
   ① **现有尺寸量**：容器 `size()`（`for (const auto& x : p->arr)` 的圈数就是它）；
   ② 与尺寸量比较的计数器（`i < n` / `i < xs.size()`）；
   ③ `.tu` 里的 `repeats` / `target` 声明。
3. **给不出上界就明确报**：`while (p)` / `while (p != nullptr)` 这类"圈数 = 链长"的
   循环报 **`E-Pointer-NoBound`**（消息里直接写"给不出上界"，并给上面三条出路）。
   **绝不写一个看起来合理的常数**——`κ` 记 ⊤ 并注明原因，是这条承诺的底线。

**空指针：静态可证的当场报，运行期真的解引用也必须留痕**

- `u64* p = nullptr; return *p;` → `E-Pointer-NullDeref`（**静态可证**：
  直线路径上的最后一次赋值就是 `nullptr`）；
- `if (p != nullptr) { *p; }` / `if (p) { *p; }` 的体内 → 守卫被认，不误报；
- **运行期**（`src/interp.py` 的 `_deref_read`）：真的解引用到空指针时抛**同名**
  `E-Pointer-NullDeref`，**不许让宿主崩**（Python 侧就是 `None` 上取字段 /
  下标，会变成 `TypeError`——那是宿主异常，不是语言诊断）。
  两条**判据不同、都要有**：静态那条判"可证"，运行期那条判"真的发生了"；
  同一个程序里两条可以同时出现（静态先报，`--no-check` / 绕过 check 时运行期也拦）。
  会走到运行期那条的典型写法是**指针经形参进来**：
  `u64 g(u64* p) { return *p; }` + `g(nullptr)`——静态证不出来，
  运行期必须报。

**别名与值语义：冲突只有一处，写在这里**

这门语言的核心承诺是**值语义 + 逐点拷贝**（[语法清单](语法清单.md) §七个拷贝点）：
声明初始化、赋值、按值形参、按值返回、入容器、`for` 元素绑定、struct 成员——
七处都真拷贝。**指针是唯一允许别名的地方**：

| 写法 | 语义 | 拷贝表怎么记 |
|---|---|---|
| `S* q = &s;` | `q` 指向 `s`（**别名**） | 指针是标量：拷的是地址，**不深拷** `s`（成本 0） |
| `q->field = 9;` | 改的就是 `s.field`（写穿） | `deref` / 基址是 `deref` 的 `field` 是**左值**（`_is_lvalue` 已含 `deref`），走"改写"而不是"拷贝" |
| `S t = s;` | 仍然是**拷贝** | ⑦ 结构体成员 / ① 声明初始化照旧；指针字段只拷地址 |
| `q2 = q;` | 两个指针指向同一对象 | ② 赋值：指针本身是标量，成本 0 |

> **实测（2026-11-10，`tests/cases/test_interp.py::test_pointer_runtime`）**：
> `S b = a;` 之后改 `b.f` **不影响** `a.f`（值语义未破）；
> 而 `q->f = 9` / `*p = 7` / `r = q` 三条都**改到被指的那块存储**。
> `*p = 0 - 1;` 落进去的是 `2^64-1`（按**指向类型**转换，不是裸 `-1`）。

**为什么可以接受**：值语义的七个拷贝点是为了"改一个绑定不会悄悄改到另一份"。
指针把"共享"写成**显式语法**（`&x` 取地址、`*p` / `p->f` 写穿），读者看得见；
其余路径仍然逐点拷贝。所以口径是：**除了显式指针，任何地方都不产生别名**——
引用形参本来就不拷贝（也不写回标量），局部 `T&` 仍然直接拒绝（`E-Ref-Local`）。
**`&x` 作为引用形参的显式借用标记**（`take(&a)`，`calculator` 样例依赖）不受影响：
`T&` / `const T&` 形参收到的是**被指的那个对象本身**（别名不变），
`T*` 形参才按值收下地址。

**接线清单（2026-11-10 晚：**运行期 1–4、6 已接完**；第 5 条是 `typecheck.py` 的 4 行，随另一路一起删）**

### 2.3 判据 C：契约表达不了（**`Cost` 的边界**）

这一节不是"语法不支持"，是"**这门语言的承诺本身做不到**"。判据：`target` 的成本式是一套**固定的阶代数**——`(多项式次数, log 个数, loglog 个数)` 三元组 + 有理次幂 + 除法（[语法清单](语法清单.md) §分数次幂 / §loglog）。

> **先说清范围（2026-11-10 补）**：这门语言只承诺「**每一次调用的最坏上界**」——**不承诺期望复杂度，也不承诺摊还复杂度**。
> 所以下面两条**不是缺陷，是模型之外**：
> - **期望复杂度**（跳表 / 哈希表 / 随机化快排）：随机化结构本来就**没有最坏 `log n`**，诚实契约就是 `O(n)`。写 `O(log n)` 才是撒谎。
> - **摊还复杂度**（并查集的 `α(n)`、动态数组 `push` 的 `O(1)`）：摊还是「**一串操作的总账**」，而这里的契约是「**单次调用**」。**不是判据算错了，是判据没有这个词汇，也不需要**——松（写 `O(n)`）是安全的，而"紧"从来不是目的。
>
> **注意一个容易混的点**：并查集**只加按秩合并**时，**单次** `find` 的最坏就是 `O(log n)`——**那不叫摊还**。工具算不出它是 **κ 的推导太粗**（把 `while (parent[r] != r)` 记成 n 圈，κ = 53n+63），属于**分析器 gap**，与摊还无关。

| 你想写 | 实际 | 实测 / 出处 |
|---|---|---|
| 摊还 `O(1)`（并查集、哈希表、`deque` push） | 只能按**最坏**记；n 次调用就是 `O(n)` | §2.3.1 |
| `α(n)`（逆 Ackermann） | `E-Target-BadForm`（target）/ `E-Repeats-UndefinedName`（repeats） | §2.3.2 |
| `n!` | **工具链崩（traceback）**，不是干净诊断 | §2.3.3 |
| `2^n` / `pow(2, n)` / `n^{log n}` | `E-Target-BadForm` | §2.3.3 |
| 常数因子（`14n` vs `n`） | 只判阶，不算系数 | [介绍](介绍.md) §3「口径」：κ 是上界、可以松 |
| `O(n^2)` | 成本式里没有 `^` → `E-Target-BadForm` | 写成 `O(n * n)` |
| `O(n % 3)` | `%` 不在成本式里 | [语法清单](语法清单.md) §除法 |
| `n / m`（两个尺寸量） | 判阶 `⊤`（"判不了"，不猜） | [语法清单](语法清单.md) §除法 |
| 多尺寸量：`κ = n×m` 要过 `O(n + m)` | 判**债务**（可证超出：target 每一项都缺一维）；换成 `O(n² + m)` 就只判"判不了"（不可比） | `src/cost_domain/cost_check.py` 的 `_multi_exceed` |
| 三层 `log(log(log(n)))` | 判阶"判不了"（家族到此为止） | [语法清单](语法清单.md) §loglog |

#### 2.3.1 摊还：**这是最容易撞的一条**

`Cost` 里没有"摊还"这个维度。每次调用按**常数**记，所以**总代价就是调用次数**。
实测（路径压缩的并查集 `find`，`parent` 是 `vector<u64>`）：

```text
target { time: { max: O(1) }, };
…
$ elench cost uf
▲ find  κ ≤ 2 + n(parent)×13 + 2
        **超标**：阶不够
▲ 1 处超出 target（time / allocation 各算一处；记为债务，不阻断构建）
```

单次 `find` 在真实数据上接近常数，但契约**只能承诺 `O(n)`**（最坏是一条长链）。
**桶/哈希也一样**：`map` / `set` 被实现成 AVL，承诺**最坏 `O(log n)`**，就是为了让"上界"真的是上界（[语法清单](语法清单.md) §为什么 map/set 是平衡树）。
`unordered_*` 存在，但承诺**最坏 `O(n)`**——"它存在的意义是与 C++ 对齐，不是更快"（[语法清单](语法清单.md) §unordered_map）。

**怎么办**：target 写最坏阶（`O(n)` / `O(log n)`），在 `.tu` 的注释里写清"实际期望是摊还 O(1)"；`vector` 的扩容那一次由 `allocation` 维度单独记（[语法清单](语法清单.md) §allocation 的口径）。

#### 2.3.2 `α(n)`：连 `repeats` 也不认

```text
target { time: { max: O(alpha(n)) }, };
✗ E-Target-BadForm @2:5  target.time.max 的成本式认不出：支持 整数 / O(size) / x.size() / log(x) / k(f) / 四则运算（`+ - * /`） / sqrt(x) / root(x, q) / pow(x, p/q)；除法只认 `n / log(n)` / `n / 2`（分母是另一个尺寸量时判不了阶）

repeats alpha(n);
✗ E-Repeats-UndefinedName @2:5  f 的 repeats 引用了未定义的名字 `alpha`：repeats 运行时只按**谓词自己的形参**（n）与模块级常量求值，别的名字求不出来。
```

**连"循环次数的上界"这条旁路也堵死了**：`repeats` 只认自己的形参、模块级常量，以及 `log` / `log2`（[语法清单](语法清单.md) §repeats）。

#### 2.3.3 `n!` / `2^n` / `n^{log n}`：不在阶代数里

```text
target { time: { max: O(2^n) }, };            → E-Target-BadForm
target { time: { max: O(pow(2, n)) }, };      → E-Target-BadForm
target { time: { max: O(n!) }, };             → traceback（见下）
```

`n!` 比其他两个更糟：**它现在会让 `check` 直接崩**，而不是给一条可读的诊断：

```text
ValueError: restart 不许触碰 target（契约持久、实现一次性；要改 target 请人工编辑）：
在 .tu 末尾插入 spec 骨架（target 要你自己填）
```

这是 `checker.py` 里一条"restart 不许触碰 target"的断言被错误路径触发（`O(n!)` 里的 `!` 让 spec 解析失败，随后 `E-Fn-NoSpec` 的修法动作去构造一个改 target 的 restart）。
**在修好之前**：不要把 `!` 写进成本式。真要写阶乘级，就按你能承诺的那个多项式写（例如 `O(n * n)`），并在 `.tu` 的注释里说明"它比真实阶松"——**别让它看起来像个精确的承诺**。

#### 2.3.4 为什么真指数"故意不给"

**不是漏了，是不给。** 理由一句话：

> 把 `O(2^n)` 当 target，对**任何**有限 κ 都成立——最坏情况下 `κ(n) ≤ 2^n` 几乎恒真。
> 一条**永远被满足**的承诺，等于没有承诺。

这和"target 只收不能放"（[语法清单](语法清单.md) §`target` 的槽位）、"不检查 target 写得过松"是同一套取舍：工具只回答"实现是否在上界之内"，紧度由作者负责。
真要表达指数级，现在只能写成 `O(n * n * n …)` 这种有限多项式，**并接受它是松的**。

#### 2.3.5 一个正面提醒

阶代数**比你以为的宽**：`√n`、`n^(2/3)`、`n^(3/2)`、`n / log n`、`n log log n` 都能写（[语法清单](语法清单.md) §分数次幂 §除法 §loglog）。撞墙之前先翻那一节。

## 3. 能写但跑不动（性能）

### 3.1 SHA-256 实测

搬到这门语言里的 SHA-256（`sha256.tu` / `sha256.eln`，逐字节对照 `hashlib` 正确）：

| 输入 | Elench（解释器） | Python `hashlib` | 慢多少 |
|---|---|---|---|
| 1 KB | **0.404 s / 次** | 0.530 µs | **≈ 76 万倍** |
| 64 KB | 32.0 s | 13.3 µs | ≈ 240 万倍 |
| 1 MB | **564.9 s** | 208 µs | **≈ 270 万倍** |

单位是**每次哈希的墙钟**（不是吞吐）。同一份记录里还有操作数：1 KB → `308,126` ops（`300.9` ops/byte）、1 MB → `310,383,422` ops（`282` ops/byte）。
契约侧：`κ = 21·n + 62`，`target { O(n) }` → **判"达成"，比值 ≈ 21**。

> **本文写作时复跑**（同一台机器、负载高于当时）：1 KB → `0.400 s`（按 1 KB / 10 KB 的差分算单位成本），
> 1 MB → `567 s`；1 MB 的 digest 与 `hashlib` **逐字节一致**。数量级与上表相同。

### 3.2 这说明什么、不说明什么

- **说明的是解释器的量级**：约 `0.55 M ops/s`（3 亿操作跑了 565 秒）。慢 3 个数量级来自"每个操作都要过一遍 Python"，**不是**来自契约或语言设计。
- **不说明契约是假的**：`κ = 21n+62` 是**操作数上界**，实测 `ops` 是它的 **13–14 倍**（常数因子），方向仍是 `ops ≤ κ`（[语法清单](语法清单.md)："`κ ≥ ops` 只说明承诺覆盖了解释器做过的事，不是性能承诺"）。
- **不说明这门语言慢**：仓库里**没有 C++ 后端**（[语法清单](语法清单.md) §和 C++17 的对应："`src/cxx_map.py` 只是映射表，不是代码生成器"）。想要机器速度，现在唯一的出路是 **FFI**：`extern … from "lib"` + `link` + `unsafe { }`，并在 `external { … }` 里如实登记成本。

### 3.3 什么活适合它、什么活别用它

| 适合 | 别用 |
|---|---|
| 小输入（≤ 几 KB）的算法原型 + 契约 | 吞吐/延迟敏感的热路径（哈希、压缩、编解码） |
| 想**证明**"这个实现没超上界" | 想要"跑得快"（那是后端的事，现在没有） |
| CI 里挡"AI 把 O(n) 写成 O(n²)" | 流式/大文件处理（1 MB 要 9 分钟） |
| 多候选 `?!` 的**相对**比较（同机同规模） | 跨语言绝对性能对比（会得出上面那张 270 万倍的表） |

### 4.2 四个成对的例子（都跑过）

**① 整数平方根—— `sqrt` 只收 `f64`，`u64` 开方仍要自己写**

（`sqrt(16.0)` 现在有内建、返回 `4.0`；但 `u64` 开方要精确整数，别绕 `f64`——
超过 2^53 会丢位。所以这条二分依旧有用。）

整数 `/` 现在返回**普通整数**（除零是运行期陷阱 `E-Div-ByZero`，不再是 `Result`），
所以这里可以直接写 `/ 2`：

```elench
spec isqrt(u64 n) -> u64 {
    target { time: { max: O(1) }, };
}
```

```elench
pub u64 isqrt(u64 n) {
    u64 lo = 0;
    u64 hi = n;
    if (hi > 4294967295) { hi = 4294967295; }
    for (u64 i = 0; i < 64; i = i + 1) {
        if (lo >= hi) { break; }
        const u64 mid = lo + ((hi - lo + 1) / 2);
        if (mid * mid <= n) { lo = mid; } else { hi = mid - 1; }
    }
    return lo;
}
```

实测 `isqrt(1000) = 31`。（固定 64 圈是因为 `u64` 最多 64 位；想写 `O(log n)` 就用 `while` 并在 `.tu` 里写 `repeats`。）

**② 浮点平方根（牛顿迭代）—— `f64` 的 `/` 是 IEEE 除法**

> **2026-11-10 起三条更短的写法**：`sqrt(2.0)`、`2.0 ** 0.5` → `1.4142135623730951`
> （`sqrt` 是内建、`**` 是真幂，§2.2.1）。这一节保留，因为它演示的是"浮点
> `/` 的除零走 IEEE（`inf`/`nan`）"这条规则，而且牛顿迭代是**没有 `sqrt` / `**` 时**的写法。
> **三者不是逐位相同**（实测）：牛顿 30 圈给 `1.414213562373095`，
> `2.0 ** 0.5` 给 `1.4142135623730951`——差 1 ulp（`fsqrt(2) == 2.0 ** 0.5`
> 实测 `False`）。要"正确舍入"的平方根就用 `sqrt`（或 `** 0.5`）；
> 牛顿那版是**迭代够用**，不是同一个结果。

```elench
spec fsqrt(u64 n) -> f64 {
    target { time: { max: O(1) }, };
}
```

```elench
pub f64 fsqrt(u64 n) {
    f64 x = n as f64;
    for (u64 i = 0; i < 30; i = i + 1) {
        if (x <= 0.0) { break; }
        x = 0.5 * (x + (n as f64) / x);
    }
    return x;
}
```

实测 `fsqrt(2) = 1.414213562373095`。**`f64` 除以 0 是 IEEE `inf`/`nan`，不是 `Err`**（[语法清单](语法清单.md) §整数溢出："浮点除零走 IEEE inf/nan"）。

**③ 链表 / 树：用 index 模拟（指针能跑，但链长给不出上界 → κ 只能 ⊤）**

两个平行数组：`values[i]` 是值，`nxt[i]` 是"下一条的下标"，`0` 当空哨兵。

```elench
spec sum_list(const vector<u64>& values, const vector<u64>& nxt) -> u64 {
    target { time: { max: O(values.size()) }, };
}
```

```elench
pub u64 sum_list(const vector<u64>& values, const vector<u64>& nxt) {
    u64 s = 0;
    u64 i = 1;
    for (u64 k = 0; k < values.size(); k = k + 1) {
        if (i == 0) { break; }
        s = s + values[i];
        i = nxt[i];
    }
    return s;
}
```

实测 `values=[10,20,30]`、`nxt=[0,2,0]`、`head=1` → `50`。
**注意循环写成 `for` + `break`**：`while (i != 0) { }` 会让 `check` 报 `E-While-NoBound`（"无法确定 while 的迭代次数"；**行首是 ⚠，不阻断构建**，但没有上界可用，κ 只能给 ⊤）。

**④ `Result` 替代异常**

```elench
error CalcError;

spec divide(u64 a, u64 b) -> u64! {
    requires b != 0;
    target { time: { max: O(1) }, };
}
```

```elench
u64! divide(u64 a, u64 b) {
    if (b == 0) {
        return Err(CalcError::DivByZero);
    }
    return a / b;
}
```

实测 `divide(7, 2) = 3`。三条硬规则见 §2.1.4（`error` 必须声明、`return x` 自动 `Ok`、`?` 要求 `T!`）。

### 4.3 顺手记住的六条

1. **`**` 是幂**（2026-11-10 修；以前是两个 `*`，`2 ** 10` 静默得 `20`）；`*x` / `&x` / `goto` / 未知类型名**都明确报错**（§2.2.1、§2.1.1）——它们以前"不报错、也不做事"。
2. **整数除法和取模返回普通整数**（不再包 `Result`）；**除零 / 对 0 取模是运行期陷阱 `E-Div-ByZero`**——要给友好错误就在除之前判零，要声明前提就在 `.tu` 写 `requires b != 0;`。
3. **`while` 的条件必须能被尺寸表达式界定**，否则 `E-While-NoBound`；`for (u64 i = 0; i < n; i = i + 1) { }` 天然可以（条件与尺寸量比较）。
   C 三段式 `for (init; cond; step)` 等价于 `init; while (cond) { body; step; }`，也按同一条规则判——
   推不出就 `⊤` + 原因，不会给一个小数字。
4. **`.eln` 里只有函数实现**：`error` / `const` / `enum` / `struct` / `spec` 都在 `.tu`（[语法清单](语法清单.md) §1）。函数只写 C++ 形状 `u64 f(…)`；`func f(…) -> T` 已下线（`E-Func-KeywordRemoved`）。
5. **`const vector<T>&` 是只读借用**：`sort` / `sort_by` / `vec_push` 这类原地内建会报 `E-Const-Mutate`，要改就别加 `const`（[语法清单](语法清单.md) §const 与嵌套容器）。
6. **`val` 是退役关键字**，连参数名都不能用：`u64 f(u64 val)` → `E-Decl-OldKeyword`；**`char` / `int` / `string` 不再是关键字**（R1 起是类型拼写，可以当普通名字用，但别这么写）。

## 5. 一页速判

写之前问三个问题，30 秒能定：

1. **它需要地址、类型参数化、继承、异常、闭包吗？**
   需要 → 判据 A，**换个设计**（§4.1）。不报错的假通过尤其危险（§0.1）。
2. **它需要 `sin` / `cos` / `exp` / `log`（自然对数）吗？**
   需要 → 判据 B，**自己写**（级数 / 二分，§4.2）。
   **`sqrt` / `log2` / `floor` / `ceil` / `round` / `fabs` / `abs` /
   `popcount` / `clz` / `ctz` 已经是内建**（§2.2.1，全 `O(1)`）；
   幂用运算符 `**`（`x ** 0.5` = 浮点平方根 = `sqrt(x)`）。
3. **它的 target 里出现 `α(n)` / `n!` / `2^n` / 摊还吗？**
   出现 → 判据 C，**写最坏阶**并在注释里说清预期（§2.3）。

| 你的直觉 | 这门语言的态度 |
|---|---|
| "先写出来，性能以后再说" | 可以，但 `check` 会先要你交 `target` |
| "这个操作 O(1)"（摊还意义上） | 契约不认摊还，按最坏写 |
| "加个模板/宏就通用了" | 只有 `T f<T>(…)` 最小切片；没有类模板、没有宏系统（`#define` 只是预处理展开） |
| "用指针/引用传出去" | 指针已能跑（§2.2.6），但**逃逸的局部地址**（`return &s;`）在 C++ 里是 UB，本语言暂不查生命周期；推荐 `vector<T>&` 借用或返回索引 |
| "抛个异常" | `T!` + `Err(...)` |
| "慢就换个后端" | 现在没有后端；只有 FFI（§3.2） |

## 6. 自己复核：探针方法与复现命令

**每个结论都是这样跑出来的**（约 30 秒一条）：

```bash
# 1) 在临时目录里写一对模块（.tu 是契约、.eln 是实现）
$ mkdir /tmp/p && cd /tmp/p

# 2) 看它是"报错"还是"静默通过"
$ python -B <repo>/src/elench.py check p          # 诊断（看行首：✗ error / ⚠ warning）
$ python -B <repo>/src/elench.py run p --fn=f --u64=16   # 真正的判据：值对不对
$ python -B <repo>/src/elench.py parse p.eln      # 怀疑"它被解析成了别的什么"时
```

2. **怀疑语法被误读时用 `parse`**——`goto done;` 变成 `var-decl` 就是这么发现的。
3. **`cost` 才看得到契约的结论**——`check` 只查语法/类型/契约形态，`done` / `debt` / `⊤` 由 `elench cost` 判（[退出码与CI](退出码与CI.md)）。

## 附录 A 值语义的边界（2026-11-10）

**一句话**：这门语言能做到「**默认值语义**」，做不到「**只有值语义**」。

### A.1 值语义表达不了什么

```cpp
char** argv                       // 指向指针的指针
const Json* get(...)              // 借用 / 可空引用
struct Json { Json* children; }   // **树** —— 共享结构
```

「树 / 图 / 共享」这类结构，值语义表达不了（要么无限展开，要么复制爆炸）。C++ 里靠指针，Rust 里靠 `Box`/`Rc`。
**这是表达力问题，不是实现选择。**

### A.2 划分

| | 规则 |
|---|---|
| **所有权** | **只有值**（`vector` / `map` / `struct` / `array`）—— 唯一的所有权模型 |
| **借用** | `const T&`（只读）、`T*`（可空/可重定向的借用） |
| **手工生命周期** | **仍然拒绝** `new` / `delete` |

**没有裸 `new`/`delete`，就没有手工生命周期。** 但**堆所有权仍然存在**——它必须通过「受管类型」（`unique_ptr` 或容器）表达。
**受管类型目前还没有**，所以今天手写链表的唯一可行写法是**索引池**（见 A.3）。

### A.3 手写链表的三条路

| 写法 | 所有权在哪 | 遍历上界从哪来 | 今天能不能写 |
|---|---|---|---|
| **索引池**（推荐） | `std::vector<Node>`（值） | `pool.size()` | ✅ **能** |
| `std::unique_ptr<Node>` | 受管类型 | 链长 → 需 `alloc` | ❌ 类型还没加 |
| `std::list<T>` | 标准容器 | `xs.size()`（C++11 起 O(1)） | ❌ 还没映射 |
| 裸指针链 | 无（`new/delete` 被禁） | 需 `alloc` | ❌ **写不了，且不该写** |

**索引池示例**（成本可证，因为上界是 `pool.size()`）：

```eln
struct Node { u64 next; u64 value; }
struct List { std::vector<Node> pool; u64 head; u64 npos; }
```

### A.4 为什么这仍然是划算的

```
没有任何指针的函数  →  完全值语义  →  别名不存在  →  编译器可以随便优化
出现指针的函数      →  别名可能存在  →  优化变保守  →  只影响这些函数
```

**CSAPP 第 5 章说「别名让编译器不敢优化」——我们的损失被限制在「签名里有指针的函数」上，
而算法库的绝大多数函数本来就不需要指针。**

## 附录 B 默认优化与 `check`：把 C++ 白拿的优化换成"可检查的假设"（2026-11-11 定，**待实现**）

### B.1 问题：我们比 C++ 慢在哪

我们**定义了回绕**（`i32` 溢出就 wrap）、**给 `at()` 加了边界检查**——安全，但这两样都是 C++ **白拿**的优化：

```
C++：有符号溢出是 UB → 编译器可以假设"不溢出" → 强度削弱、归纳变量、部分向量化
我们：定义了 wrap   → 编译器必须尊重 wrap     → 优化被挡
C++：operator[] 无检查
我们：at() 有检查（安全，但热循环里每次多一次比较+分支）
```

### B.2 决定：**优化默认开，检查默认也开**

```elench
// doc-template: 附录 B 是设计说明；`check { … }` 顶层子句还没接线（P5）
// .tu —— 默认就开这两项检查，写出来只是为了改
check { overflow, outbound };

spec count(const vector<u8>& text) -> u64 { … }
```

| 项 | 检查什么 | 违反时报 |
|---|---|---|
`overflow` | **有符号**整数运算不溢出 | `E-Overflow` |
`outbound` | `xs[i]` 的下标在界内 | `E-OutOfBounds` |

**三句话说完语义**：

```
① 优化默认开（release）：有符号算术按"不溢出"优化；`xs[i]` 无边界检查
② 检查默认开（debug / run / 测试）：违反就报上面两个码，**不许无声 UB**
③ 报告里列出这个模块开了哪些 check —— **声明了什么，运行期就校验什么**
```

**这跟 C++ 的差别不是"快不快"，是"UB 还是可查"**：C++ 同样快，但越界/溢出是无声的。

### B.3 无符号与有符号必须分开

```
u64 / u32 / u16 / u8   → **回绕是免费的**（硬件本来就是模运算），不需要"假设不溢出"
i64 / i32 / i16 / i8   → **溢出才需要假设**（C++ 在这里是 UB）
```

**所以默认优化只对**有符号**生效**，无符号照旧是定义好的回绕。

### B.4 要回绕的地方：给**精确的运算符**，不给模块开关

```elench
// doc-template: `+%` / `-%` / `*%` 运算符还没接线（P5）
a +% b     a -% b     a *% b        // wrapping 加法/减法/乘法（与 Rust / Swift 同形）
```

**为什么不做模块级开关**：哈希、加密、校验和需要回绕，但它们通常只是**几个表达式**。
模块级"关掉优化"会让整个模块变慢；**运算符级精确、局部、一眼看出**。

### B.5 `at()` 与 `[]` 的分工

| 写法 | 边界检查 | 用在哪 |
|---|---|---|
`xs[i]` | **无**（默认优化） | 热循环，下标已由循环条件保证 |
`xs.at(i)` | **有**（永远） | 下标来路不明、或想显式要安全 |

**两者都是语言的一部分**：`[]` 是"我知道它安全"，`at()` 是"让工具替我确认"。

### B.6 明确不做

```
✗ `assume { no_overflow };`     —— 名字用检查对象（`overflow`），不用否定式；而且旧 `assume`（不可验证的成本假设）已退役，别再撞名
✗ `?fast { … }` 块级            —— 常见情况是全文，块级只会变成"每个函数包一层"
✗ 模块级"关掉优化"开关           —— 用 `+%` 等运算符，精确到表达式
✗ 把检查做成可关的调试开关        —— 和 `guarantees` 同一条哲学：**可关掉的断言等于默认关掉的断言**
```

### B.7 实现的验收标准（写在这里，实现时照着做）

```
① release 生成的 C++ 里：有符号算术无溢出检查、`xs[i]` 是 operator[]
② debug/run 里：越界报 E-OutOfBounds（带下标与长度）、溢出报 E-Overflow（带两个操作数）
③ `+%` 在任何构建下都不检查，且语义是 mod 2^位宽
④ 报告列出模块的 check 项
⑤ 现有 17 个样例默认全部通过（它们本来就下标合法、不溢出）
```
